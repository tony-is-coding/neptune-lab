## 1. 产品定位

**Neptune-AI = 培养专属 AI 员工的企业平台。**

目标用户是非技术业务人员。他们不是在"用 AI 聊天"，是在"配置和培养 AI 下属" — 配好岗位说明书，接入企业数据，Agent 就能上岗工作，并且随时间越来越胜任。

Agent 是产品的一等公民。

## 2. 核心设计判断

### 2.1 原子单元

| 视角 | 原子单元 | 说明 |
|------|---------|------|
| 用户视角 | Agent | 用户的心智模型是"我和一个 Agent 在长期协作" |
| 技术视角 | Session | SDK 围绕 Session 运转，但用户无需感知 |

**一个 Agent = 一个持续对话流**。用户不需要管理"创建会话"、"切换会话"，选择 Agent 后直接进入唯一的长期对话界面。上下文窗口管理由框架在后台处理（用户看到完整历史，Agent 看到优化后的上下文），用户无感。

如果需要一个新的开始，用户创建一个新的 Agent（新的角色），而不是清空当前 Agent 的对话。

### 2.2 产品边界

**Neptune-AI 管编排层，不管执行层。**

| 管的 | 不管的 |
|------|--------|
| Agent 模板管理（岗位说明书） | Agent 如何思考（prompt 效果） |
| Session 生命周期编排 | 工具如何执行（SDK 能力） |
| 用户与权限 | 模型调用与重试（SDK Provider） |
| MCP Server 注册（地址 + 认证） | MCP Server 运行时（客户 IT 部署） |
| 用量与计费 | |
| 审计与追溯 | |

**明确不做：**

- AI 模型训练/微调
- 代码编辑器
- 流程引擎/BPM（Agent 自主决策，非编排式 RPA）
- 实时通讯（不是 Slack/Teams）

### 2.3 技术选型决策

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 部署形态 | 纯 SaaS 托管 | 产品定位为 SaaS 服务 |
| 基础设施 | Docker Compose（MVP） | 先跑通，不做云绑定 |
| 租户隔离 | 共享数据库 + tenant_id | MVP 3-5 租户，成本最低 |
| 文件存储 | 本地文件系统 + 租户目录隔离 | `/data/tenants/{tenantId}/workspace`，TenantPermissionDelegate 限制路径 |
| DB 迁移 | Drizzle Kit + 带版本号 migration | 支持 up/down，启动时自动检测 |
| API 版本 | `/api/v1/` 前缀 | 破坏性变更升级版本号 |
| SDK 依赖 | Workspace 依赖 | 同仓库开发，迭代最快 |

## 3. 用户模型

**极简两角色，一个字段区分：**

| 角色 | 标识 | 核心职责 | 核心动作 |
|------|------|---------|---------|
| 管理员 | `role: 'admin'` | 造工具（配 Agent、接数据、管人） | 配置 |
| 用户 | `role: 'user'` | 用工具（和 Agent 协作完成任务） | 对话 |

**统一应用，角色决定可见功能。** 不拆分为管理后台和用户前端。一个桌面端 App，管理员比普通用户多看到配置入口。

## 4. 信息架构

```
首页 = Agent 列表（我的 Agent 们）
│
├─ 点击某个 Agent → 对话界面
│   ├─ 实时流式响应（SSE）
│   ├─ 工具调用可视化（卡片展示）
│   ├─ 历史记录滚动浏览（无限滚动）
│   └─ 无"新建会话"按钮 — 一个 Agent 只有一个持续对话
│
├─ [Admin] Agent 模板管理
│   ├─ 创建/编辑模板（system prompt、工具、skills）
│   ├─ MCP Server 注册
│   └─ 模板启停
│
├─ [Admin] 用户管理
│   └─ 租户内用户的增删改查、角色分配
│
├─ [Admin] 用量/计费
│   └─ Token 用量、成本统计
│
└─ 设置
    └─ 个人信息、API Key 配置
```

## 5. 核心产品能力

### 5.1 能力清单

| 编号 | 能力 | 说明 | 优先级 | 对应角色 |
|------|------|------|--------|---------|
| C1 | Agent 模板管理 | 创建/编辑 Agent 的"岗位说明书"：名称、system prompt、工具选择、skills、MCP 接入、约束 | P0 | Admin |
| C2 | Agent 对话 | 选择 Agent → 直接进入对话界面，SSE 流式响应，工具调用可视化 | P0 | User |
| C3 | Agent 工作记忆 | Agent 按自身维度记住用户关键信息，随时间积累理解，越来越懂用户 | P0 | 系统 |
| C4 | MCP Server 注册 | 配置企业数据源连接（地址、认证信息），供 Agent 模板引用 | P0 | Admin |
| C5 | 对话历史 | 用户可回顾与 Agent 的完整交互历史，无限滚动浏览 | P1 | User |
| C6 | 用户管理 | 租户内用户增删改查、角色分配 | P1 | Admin |
| C7 | 用量计费 | Token 用量追踪、成本统计、租户级账单 | P1 | Admin |

### 5.2 能力依赖关系

```
C4 (MCP 注册) ──→ C1 (Agent 模板) ──→ C2 (Agent 对话)
                                        ↓
                                   C3 (工作记忆)
                                        ↓
                                   C5 (对话历史)

C6 (用户管理) ── 独立
C7 (用量计费) ── 依赖 C2 的 token 事件
```

## 6. Agent 工作记忆

### 6.1 产品概念

"越来越懂用户的 Agent"依赖工作记忆。工作记忆是 Agent 在对话中主动提取和记住的关键信息，与对话历史不同：

| 维度 | 对话记忆（transcript） | 工作记忆（memory） |
|------|---------------------|-------------------|
| 内容 | 完整对话原文 | 提炼后的关键事实 |
| 容量 | 受上下文窗口限制 | 独立存储，不占上下文 |
| 生命周期 | 随 Session 存在 | 跨 Session 持久 |
| 作用 | Agent 看到近期对话 | Agent 加载到 prompt 开头 |

### 6.2 作用域

**按 Agent 隔离。** 同一用户的不同 Agent 拥有独立记忆。

理由：每个 Agent 是不同的"岗位角色"，它对用户的理解应该和岗位相关。财务助手记住的是用户的报销偏好，数据分析师记住的是用户的指标口径。

### 6.3 框架升级推导

产品需求"按 Agent 隔离记忆"推导出框架需要升级记忆存储的作用域机制：

**方案：ScopedMemoryStore 装饰器**

框架层（SDK）：
- `IMemoryStore` 接口不变，保持向后兼容
- 新增 `ScopedMemoryStore` 装饰器类，实现 `IMemoryStore`
- 构造时接收基础 store + scope 前缀
- 所有操作自动 prepend scope 前缀

产品层（Neptune-AI）：
- 创建引擎时包装：`new ScopedMemoryStore(baseStore, agentId)`
- 框架不引入 `agentId` 概念，产品决定作用域维度

```
RedisMemoryStore → ScopedMemoryStore(agentId) → AgentEngine

存储 key: {prefix}:{agentId}:{userId}:{memoryKey}
```

## 7. 用户旅程

### 7.1 管理员旅程

```
登录
 → 进入 Agent 列表页
 → 创建新 Agent 模板
    → 输入名称和描述（"财务助手"）
    → 编写 system prompt（岗位职责）
    → 选择工具（读文件、搜索、代码执行）
    → 挂载 MCP Server（连接公司 ERP）
    → 设置约束（每轮最大 token 数）
 → 保存并激活
 → 通知团队成员可以使用
 → 查看租户级用量统计
```

### 7.2 用户旅程

```
登录
 → 进入 Agent 列表页（看到管理员配置好的 Agent 们）
 → 点击"财务助手" → 进入对话界面
 → 输入："帮我分析下这个季度的预算执行情况"
 → 观察 Agent 响应：
    → 思考过程（文字流式输出）
    → 调用工具（卡片展示：正在查询 ERP 数据...）
    → 输出分析结果
 → 继续追问或给出反馈
 → 下次打开同一个 Agent → Agent 记得上次的对话和偏好
 → 任务完成 → 直接离开，无需"关闭会话"
```

## 9. 工程规范方向

### 9.1 DB 迁移规范

- 使用 Drizzle Kit 生成 migration SQL
- 每个 migration 带版本号：`0001_create_sessions.sql`
- 必须包含 up 和 down 脚本
- 服务启动时自动检测并执行未应用的 migration
- Migration 文件纳入版本控制，禁止手动修改已发布的 migration

### 9.2 API 版本规范

- URL 前缀 `/api/v1/`
- 破坏性变更（字段删除、语义变化）升级版本号
- 非破坏性变更（新增字段、新增端点）在当前版本内迭代
- 旧版本保留至少 2 个版本

### 9.3 版本迭代规范

- 语义化版本号：`MAJOR.MINOR.PATCH`
- CHANGELOG.md 记录每个版本的变更
- SDK 升级前必须通过集成测试验证

### 9.4 配置管理规范

- 环境变量分层优先级：环境变量 > .env 文件 > 代码默认值
- 生产环境必需的配置项在启动时校验（validateConfig）
- 敏感配置（JWT_SECRET、数据库密码）不进代码仓库
