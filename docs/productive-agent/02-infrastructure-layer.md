# 02 - 基础设施层 (Infrastructure Layer)

基础设施层是整个系统的地基。Demo 中这一层几乎不存在（直连 API、内存存储），但它是生产系统中**最值得最先投入**的一层——因为上层的所有可靠性、可扩展性都依赖于此。

```
┌─────────────────────────────────────────────────────────────────┐
│                    Infrastructure Layer                          │
│                                                                  │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌────────┐ │
│  │  LLM Gateway  │ │  Knowledge   │ │ Message Queue │ │ State  │ │
│  │              │ │    Store     │ │  & Event Bus  │ │ Store  │ │
│  └──────────────┘ └──────────────┘ └──────────────┘ └────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

## 2.1 LLM Gateway（LLM 网关）

### 为什么 LLM Gateway 是改造第一优先级

LLM 是整个 Agent 系统最大的**单点故障源**和**成本变量**：

```
LLM 的不确定性：
  • 服务可用性：OpenAI/Anthropic 偶尔宕机或限流
  • 响应延迟：从几百毫秒到几十秒不等
  • 输出质量：同一输入可能产生不同输出
  • 成本：按 Token 计费，消耗随使用量线性增长
  • 模型迭代：Provider 经常更新模型，行为可能变化
```

在 Demo 中你直接 `openai.chat.completions.create()`，一行代码搞定。但在生产中，这个调用是**最脆弱的环节**——LLM Gateway 就是在这个调用前加一层保护。

### LLM Gateway 的核心能力

#### 能力一：多 Provider 抽象

**问题**：代码中到处散落着 `openai.xxx`、`anthropic.xxx` 的直接调用。要换 Provider 需要改很多地方。

**解决**：统一接口，业务代码只跟 Gateway 交互。

```
┌──────────────────────────────────────────────────────────┐
│  业务代码                                                 │
│    response = gateway.chat(messages, model="gpt-4")      │
│    # 不关心底层是 OpenAI、Anthropic 还是 Azure            │
└───────────────────────┬──────────────────────────────────┘
                        ↓
┌──────────────────────────────────────────────────────────┐
│  LLM Gateway                                             │
│                                                          │
│  model="gpt-4" → 路由到 OpenAI API                      │
│  model="claude" → 路由到 Anthropic API                   │
│  model="gpt-4-azure" → 路由到 Azure OpenAI              │
│  model="local-llama" → 路由到本地推理服务器               │
│                                                          │
│  统一输入格式 (OpenAI-compatible)                         │
│  统一输出格式 (标准化 response)                            │
│  统一错误处理 (异常转换为标准错误码)                       │
└──────────────────────────────────────────────────────────┘
```

**推荐工具**：

| 工具             | 特点                                             | 适用场景        |
| -------------- | ---------------------------------------------- | ----------- |
| **LiteLLM**    | Python 库，100+ Provider 支持，OpenAI-compatible 接口 | Python 项目首选 |
| **OpenRouter** | SaaS 服务，统一 API，自带负载均衡                          | 不想自建时       |
| **自建薄封装**      | 完全可控，但需要维护                                     | 有特殊需求时      |

#### 能力二：Fallback 链

**问题**：单一 Provider 宕机 → 整个系统不可用。

**解决**：配置 Fallback 链，自动降级。

```
请求进入 Gateway
    ↓
尝试 Provider A (OpenAI GPT-4)
    ↓ 超时 / 5xx / 限流
自动切换 Provider B (Anthropic Claude)
    ↓ 也失败了
自动切换 Provider C (Azure OpenAI)
    ↓ 也失败了
返回降级响应（如基于缓存的回答或 "服务暂时不可用"）

每个 fallback 可以有不同的配置：
  OpenAI GPT-4:  高质量，用于主路径
  Anthropic Claude: 备选，质量相近
  Azure OpenAI:  第三备选，合规场景
  本地 Llama:    最终兜底，质量下降但保证可用
```

**Fallback 触发条件**：

| 条件 | 说明 |
|------|------|
| 超时 | 单次请求超过 N 秒 |
| HTTP 5xx | Provider 服务端错误 |
| 限流 (429) | Provider 的 Rate Limit |
| 内容过滤 | Provider 拒绝生成（触发安全策略） |
| 响应质量异常 | 输出为空、格式错误等 |

#### 能力三：限流与配额

**问题**：
1. Provider 有自己的 Rate Limit（如 OpenAI TPM/RPM），超了就被拒绝
2. 需要按租户/用户/场景控制 LLM 使用量，防止成本失控

**解决**：Gateway 层实现多层限流。

```
请求进入
    ↓
┌──────────────────────────────────────────┐
│  Level 1: Provider Rate Limit            │
│  确保不超过 Provider 的 API 限额          │
│  策略: Token Bucket / 滑动窗口           │
│  例: OpenAI TPM=100,000                  │
└──────────────────────┬───────────────────┘
                       ↓
┌──────────────────────────────────────────┐
│  Level 2: 租户配额                       │
│  每个租户有自己的 Token/请求上限          │
│  例: 租户A 每天最多 500K tokens          │
└──────────────────────┬───────────────────┘
                       ↓
┌──────────────────────────────────────────┐
│  Level 3: 用户配额                       │
│  单个用户的请求频率限制                   │
│  例: 每用户每分钟最多 10 次 LLM 调用      │
└──────────────────────┬───────────────────┘
                       ↓
┌──────────────────────────────────────────┐
│  Level 4: 任务配额                       │
│  单个任务的 Token 消耗上限                │
│  例: 单任务最多 50K tokens               │
└──────────────────────┬───────────────────┘
                       ↓
                   放行请求
```

#### 能力四：成本追踪

**问题**：LLM 调用是按 Token 计费的变量成本。如果不追踪，成本完全不可控。

**解决**：每次请求记录 Token 消耗和成本。

```
每次 LLM 调用后记录:
{
  "request_id": "req-123",
  "timestamp": "2026-05-10T15:30:00Z",
  "provider": "openai",
  "model": "gpt-4",
  "input_tokens": 1500,
  "output_tokens": 800,
  "total_tokens": 2300,
  "cost_usd": 0.046,          // 根据模型定价计算
  "tenant_id": "tenant-a",    // 成本归因
  "task_id": "task-456",      // 任务归因
  "scenario": "rag_qa",       // 场景归因
  "latency_ms": 2300          // 延迟
}
```

**成本归因维度**：
- 按租户：每个组织花了多少钱
- 按场景：RAG问答、代码生成、文档摘要各花多少
- 按任务：每个具体任务的成本
- 按时间：每小时/每天/每月的成本趋势

**成本控制策略**：

| 策略 | 说明 |
|------|------|
| **预算上限** | 租户/场景/任务级别的 Token 预算，超了就拒绝或降级到便宜模型 |
| **模型路由** | 简单请求用便宜模型（GPT-3.5/Haiku），复杂请求用贵模型（GPT-4/Opus） |
| **语义缓存** | 相同或相似的请求命中缓存，减少 LLM 调用 |
| **Prompt 优化** | 减少 System Prompt 的冗余，降低每请求的 input tokens |

#### 能力五：语义缓存

**问题**：很多用户的请求是相同或相似的（如 "这个产品的价格是多少？"），每次都调 LLM 浪费钱和时间。

**解决**：在 Gateway 层加语义缓存。

```
请求进入 Gateway
    ↓
将用户输入 Embedding
    ↓
在缓存中搜索语义相似的请求 (余弦相似度 > 阈值)
    ↓ 命中                     ↓ 未命中
直接返回缓存结果              调用 LLM
（延迟 < 10ms）               将结果写入缓存
（成本 = $0）                 返回结果
```

**缓存策略**：

| 维度 | 说明 |
|------|------|
| **相似度阈值** | 通常 0.95+ 才算命中，太低会返回不相关的缓存 |
| **TTL** | 缓存有效期，知识类问题 TTL 长（小时），时效性问题 TTL 短（分钟） |
| **缓存粒度** | 按完整请求缓存，还是按子问题缓存 |
| **缓存失效** | 知识库更新时主动失效相关缓存 |

**实现方式**：
- 简单方案：Redis + 固定 TTL + 精确匹配（只缓存完全相同的请求）
- 进阶方案：向量数据库 + Embedding 相似度匹配
- 工具：GPTCache、自建

#### 能力六：请求日志

**问题**：出了问题需要回溯「这次 LLM 调用的输入输出是什么」。

**解决**：Gateway 层统一记录所有请求/响应。

```json
{
  "request_id": "req-123",
  "trace_id": "trace-789",
  "timestamp": "2026-05-10T15:30:00Z",
  "provider": "openai",
  "model": "gpt-4",
  "request": {
    "messages": [...],
    "temperature": 0.7,
    "max_tokens": 2000
  },
  "response": {
    "content": "...",
    "tool_calls": [...],
    "finish_reason": "stop"
  },
  "metadata": {
    "latency_ms": 2300,
    "input_tokens": 1500,
    "output_tokens": 800,
    "cost_usd": 0.046,
    "cached": false
  }
}
```

**注意事项**：
- 日志量很大（每次请求几 KB），考虑采样或分级存储
- 包含用户输入和 LLM 输出，注意 PII 脱敏
- 热数据（最近 7 天）存 Elasticsearch/ClickHouse，冷数据归档到对象存储

### LLM Gateway 完整请求流程

```
请求进入 Gateway
    ↓
[1] 生成 request_id + 关联 trace_id
    ↓
[2] 语义缓存检查
    ├─ 命中 → 直接返回缓存结果 → [7] 记录日志 (cached=true)
    └─ 未命中 ↓
[3] 多层限流检查
    ├─ 超限 → 返回 429 Too Many Requests
    └─ 放行 ↓
[4] 成本预算检查
    ├─ 超预算 → 降级到便宜模型 或 返回错误
    └─ 放行 ↓
[5] Provider 路由 + Fallback
    ├─ Provider A → 成功 → ↓
    ├─ Provider A 失败 → Provider B → 成功 → ↓
    └─ 全部失败 → 返回降级响应
[6] 记录 Token 消耗 + 计算成本
    ↓
[7] 写入缓存（如果适合缓存）
    ↓
[8] 写入请求日志
    ↓
返回响应
```

## 2.2 Knowledge Store（知识存储）

RAG（Retrieval-Augmented Generation）是大多数 Agent 系统的核心能力。知识存储的质量直接决定了 Agent 回答的准确性和可靠性。

### Demo 级 RAG 的典型问题

```
Demo 级 RAG 流水线:
  文档 → 固定 512 token 分块 → Embedding → 向量库 → 余弦相似度搜索 → Top-K → 塞进 Prompt

问题:
  1. 固定分块会切断语义完整性（一句话被切成两半）
  2. 纯向量搜索无法处理精确关键词匹配（如产品编号、人名）
  3. 没有数据隔离（租户 A 能搜到租户 B 的文档）
  4. 不知道检索质量好不好（搜出来的到底相不相关？）
  5. 文档更新了要全量重建索引
```

### 分块策略详解

分块是 RAG 质量的**第一道关**。分块不好，后面的检索和生成都不可能好。

| 策略 | 方法 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **固定大小分块** | 每 N 个 token 切一段，可 overlap | 实现简单，分块大小一致 | 可能切断句子/段落，破坏语义 | 快速原型 |
| **句子级分块** | 按句子边界切分 | 保持句子完整性 | 块太小，上下文不足 | 短文本 |
| **段落级分块** | 按段落/章节边界切分 | 保持段落语义完整 | 块大小不均匀 | 结构化文档 |
| **语义分块** | 用 Embedding 相似度检测语义边界，语义变化大的地方切分 | 最佳语义完整性 | 计算成本高，需要额外 Embedding 调用 | 高质量要求 |
| **层级分块** | 同时生成多粒度（文档→段落→句子），检索时按粒度匹配 | 灵活，兼顾粒度 | 索引量大，管理复杂 | 复杂知识库 |

**推荐做法**：

```
生产级分块流水线:

  原始文档
    ↓
  [1] 文档解析: PDF/Word/HTML → 纯文本 + 结构信息（标题、段落、表格）
    ↓
  [2] 层级分块:
      生成三个粒度:
      • 文档摘要（几千 token）
      • 段落/章节（几百 token）
      • 关键句子（几十 token）
    ↓
  [3] 元数据标注:
      每个块附加:
      • source: 来源文档
      • section: 所属章节
      • page: 页码
      • tenant_id: 所属租户
      • updated_at: 更新时间
    ↓
  [4] Embedding 生成:
      用 text-embedding-3-large 或同等模型
    ↓
  [5] 写入向量数据库（带元数据过滤能力）
```

### 检索策略详解

检索是 RAG 质量的**第二道关**。

#### 策略对比

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **纯向量检索** | 用 Embedding 相似度（余弦/内积）找最相似的文档块 | 语义理解好，能处理同义词和改写 | 精确关键词匹配差，可能返回语义相似但不相关的结果 |
| **BM25 关键词检索** | 基于词频-逆文档频率的关键词匹配 | 精确匹配好（产品编号、人名） | 无语义理解，同义词匹配差 |
| **混合检索（推荐）** | 向量检索 + BM25 检索，结果融合排序 | 兼顾语义和精确匹配 | 需要同时维护两个索引 |
| **Re-ranking** | 先粗检索（Top-100），再用 Cross-Encoder 精排（Top-10） | 最终排序质量最高 | 额外的 LLM 模型调用，增加延迟 |

#### 混合检索 + Re-ranking 流程

```
用户查询: "Acme-2024 产品的退货政策是什么？"
    ↓
┌─────────────────────────────────────────────────────┐
│  并行检索                                            │
│                                                      │
│  向量检索 (Top-50)          BM25 检索 (Top-50)       │
│  ├─ "Acme 系列退换货流程"     ├─ "Acme-2024 退换"     │
│  ├─ "产品售后保障条款"        ├─ "退货政策 2024"       │
│  └─ "消费者权益保护"          └─ "Acme-2024 手册"     │
│                                                      │
│  结果融合: 取并集 + 去重 (约 70-80 条)               │
└───────────────────────┬─────────────────────────────┘
                        ↓
┌──────────────────────────────────────────────────────┐
│  Re-ranker (Cross-Encoder 精排)                       │
│  对每条结果，用专门的模型计算与查询的相关性分数        │
│  取 Top-10 最相关的                                    │
│                                                       │
│  1. "Acme-2024 退货政策: 7天无理由退换..." (0.95)     │
│  2. "Acme-2024 售后条款: ..." (0.87)                  │
│  3. ...                                               │
└───────────────────────┬──────────────────────────────┘
                       ↓
              检索结果送入 LLM 生成回答
```

**推荐工具**：
| 组件 | 推荐工具 |
|------|---------|
| 向量数据库 | Pinecone（托管）/ Qdrant（自建）/ pgvector（PostgreSQL 扩展） |
| BM25 引擎 | Elasticsearch / Meilisearch / pgvector 的全文搜索 |
| Re-ranker | Cohere Rerank / BGE-Reranker / 自建 Cross-Encoder |

### 数据隔离

**问题**：多租户场景下，租户 A 的 Agent 不能搜到租户 B 的知识。

**解决方案**：

```
方案 1: 元数据过滤（推荐）
─────────────────────────
每个文档块带 tenant_id 元数据
检索时强制附加 filter: tenant_id = "tenant-a"
几乎所有向量数据库都支持

优点: 实现简单，性能好
缺点: 需要信任向量数据库的过滤正确性

方案 2: 独立索引/Collection
─────────────────────────
每个租户一个独立的向量索引
检索时只查对应租户的索引

优点: 物理隔离，安全性高
缺点: 管理复杂，资源开销大（每个索引都有最小资源需求）

方案 3: 独立数据库实例
─────────────────────────
每个租户一个独立的数据库

优点: 最强隔离
缺点: 成本极高，只适合大型租户
```

### 知识质量监控

**问题**：索引建好了，但不知道检索质量好不好。用户说"回答不准确"，不知道是检索的问题还是生成的问题。

**监控指标**：

| 指标 | 含义 | 怎么算 |
|------|------|--------|
| **检索命中率** | 查询后是否有结果返回 | 返回结果数 / 总查询数 |
| **相关度分布** | 返回结果的相似度分数分布 | 向量相似度分数的 P50/P90 |
| **用户满意度** | 基于 RAG 回答的用户反馈 | 用户 👍/👎 比例 |
| **检索利用率** | 检索到的文档块中有多少被 LLM 引用了 | LLM 引用的块数 / 检索返回的块数 |

**当指标异常时的排查方向**：
```
检索命中率低 → 可能是分块问题（块太小/太大）或知识覆盖不足
相关度分数低 → 可能是 Embedding 模型不匹配或查询/文档领域偏移
用户满意度低 → 可能是检索质量差或 LLM 生成问题，需要分别排查
检索利用率低 → 可能是 Top-K 太大，返回了太多不相关的结果
```

### 知识更新策略

| 策略 | 方法 | 适用场景 |
|------|------|---------|
| **全量重建** | 删掉所有索引，重新分块+Embedding | 知识库结构大改时 |
| **增量更新** | 只处理新增/修改的文档 | 日常更新（推荐） |
| **版本管理** | 每个文档块有版本号，更新时创建新版本，旧版本标记过期 | 需要审计和回滚的场景 |
| **软删除** | 删除的文档标记为 deleted，不物理删除，定期清理 | 需要快速撤销删除的场景 |

## 2.3 Message Queue & Event Bus（消息队列与事件总线）

### 为什么异步是 Demo 到生产的关键转变

```
Demo 的同步模型:
  用户发 HTTP 请求 → 服务器同步执行 Agent → Agent 同步调 LLM → 同步调工具 → ... → 返回结果

  问题:
  1. Agent 可能执行几十步，耗时几分钟甚至更长 → HTTP 超时
  2. 执行过程中用户无法取消或查看进度
  3. 一个请求占住一个线程/进程 → 并发能力极差
  4. 进程崩溃 → 任务丢失，从头来过

生产的异步模型:
  用户发 HTTP 请求 → 任务入队 → 返回 task_id → 用户通过 SSE 获取进度
                          ↓
                     Worker 从队列领取 → 异步执行 → 结果存 DB → 通知用户

  优势:
  1. 请求立即返回，不阻塞用户
  2. 任务可以执行任意长时间
  3. Worker 可以水平扩展
  4. 任务状态持久化，不怕崩溃
```

### 两个不同但互补的组件

**消息队列**和**事件总线**经常被混淆，但它们解决不同问题：

```
┌─────────────────────────────────────────────────────────────┐
│                                                               │
│  Message Queue (任务分发)                Event Bus (事件广播)  │
│                                                               │
│  职责: 把任务分发给 Worker               职责: 在服务间传递事件 │
│  模式: 点对点 (一个任务只能被一个         模式: 发布/订阅       │
│        Worker 消费)                           (广播给所有订阅者)│
│  关注: 任务不丢失、按优先级执行           关注: 事件实时传播    │
│                                                               │
│  用户提交任务 ──→ Task Queue ──→ Worker 领取执行              │
│                                                               │
│  Worker 执行中产生事件 ──→ Event Bus ──→ SSE Server 推送给用户 │
│                                        ──→ 审计服务记录       │
│                                        ──→ 监控服务统计       │
└─────────────────────────────────────────────────────────────┘
```

### Task Queue 详细设计

#### 任务队列的核心能力

```
┌─────────────────────────────────────────────────────────────────┐
│  Task Queue                                                     │
│                                                                  │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │  优先级队列                                                │ │
│  │  ┌───────────┐ ┌───────────┐ ┌───────────┐              │ │
│  │  │ High      │ │ Normal    │ │ Low       │              │ │
│  │  │ 紧急任务   │ │ 普通任务   │ │ 后台任务   │              │ │
│  │  │ 立即执行   │ │ 正常执行   │ │ 空闲时执行  │              │ │
│  │  └───────────┘ └───────────┘ └───────────┘              │ │
│  └───────────────────────────────────────────────────────────┘ │
│                                                                  │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │  死信队列 (Dead Letter Queue)                              │ │
│  │  执行失败 N 次的任务自动进入死信队列                        │ │
│  │  死信队列的任务可以:                                       │ │
│  │  • 人工检查和重试                                          │ │
│  │  • 自动降级处理                                            │ │
│  │  • 分析失败原因，改进系统                                  │ │
│  └───────────────────────────────────────────────────────────┘ │
│                                                                  │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │  延迟消息                                                  │ │
│  │  • 定时任务：每天凌晨执行数据同步                           │ │
│  │  • 超时检查：任务执行超过 30 分钟自动告警                   │ │
│  │  • 重试延迟：失败后 5s/30s/5min 指数退避重试                │ │
│  └───────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

#### 任务生命周期

```
用户提交任务
    ↓
[PENDING] 任务进入队列，等待 Worker 领取
    ↓ Worker 领取
[RUNNING] Worker 开始执行
    ├─ 正常完成 → [COMPLETED] 结果存入 DB，通知用户
    ├─ 执行超时 → [TIMEOUT] 记录日志，进入重试或失败
    ├─ 需要审批 → [PAUSED] 等待人工审批
    │                    ↓ 审批通过
    │               [RUNNING] 继续
    ├─ 用户取消 → [CANCELLED] 清理资源
    └─ 执行失败 → [FAILED]
                      ↓
                 重试？
                  ├─ 是 → [RETRYING] 重新入队（可能换 Worker）
                  └─ 否 → [DEAD_LETTER] 进入死信队列
```

#### Worker 池管理

```
┌─────────────────────────────────────────────────────────────┐
│  Worker Pool                                                 │
│                                                              │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐            │
│  │Worker│ │Worker│ │Worker│ │Worker│ │Worker│            │
│  │  1   │ │  2   │ │  3   │ │  4   │ │  5   │            │
│  │ 忙碌  │ │ 空闲  │ │ 忙碌  │ │ 空闲  │ │ 忙碌  │            │
│  └──────┘ └───┬──┘ └──────┘ └───┬──┘ └──────┘            │
│               │                    │                        │
│               └──── 从队列领取 ────┘                        │
│                    新任务                                 │
│                                                              │
│  扩展策略:                                                   │
│  • CPU/内存 > 阈值 → 不领取新任务                            │
│  • 队列积压 > N → 自动扩容（加 Worker 实例）                 │
│  • 队列空闲 > M 分钟 → 自动缩容                              │
│  • Worker 异常退出 → 自动重启 + 任务重新入队                  │
└─────────────────────────────────────────────────────────────┘
```

### Event Bus 详细设计

#### 事件总线的用途

事件总线解决的核心问题是：**Agent Worker 和 SSE Server 在不同进程/机器上，Worker 产生的事件怎么传到 SSE Server 再推给客户端？**

```
为什么不能用直接调用:

  方案 A: Worker 直接调用 SSE Server API
    问题: Worker 需要知道 SSE Server 地址（耦合）
          SSE Server 挂了 Worker 也失败（级联故障）
          多个 SSE Server 实例时不知道该调哪个（路由问题）

  方案 B: 共享数据库
    Worker 写事件到 DB → SSE Server 轮询 DB
    问题: 轮询延迟高
          数据库压力大

  方案 C: 事件总线（推荐）
    Worker 发布事件 → Event Bus 广播 → 所有 SSE Server 订阅
    优点: 完全解耦、实时性好、支持多实例
```

#### 事件总线架构

```
┌──────────────┐                            ┌──────────────┐
│  Agent Worker │                            │  SSE Server  │
│              │                            │     A        │
│  执行任务     │     ┌──────────────────┐   │  订阅所有    │
│  产生事件     │────→│                  │──→│  task 事件   │
│              │     │  Event Bus       │   │              │
│  发布:        │     │  (Redis Pub/Sub  │   │  匹配到      │
│  task:123:   │     │   或 Kafka)      │   │  自己管理的   │
│  event: ...  │     │                  │   │  SSE 连接?   │
│              │     │                  │   │  是 → 推送   │
│              │     │                  │   │  否 → 忽略   │
└──────────────┘     └──────────────────┘   └──────────────┘
                             │
                             │
                     ┌──────────────────┐   ┌──────────────┐
                     │                  │──→│  SSE Server  │
                     │                  │   │     B        │
                     │                  │   │  同样的逻辑   │
                     └──────────────────┘   └──────────────┘
                             │
                             │
                     ┌──────────────────┐   ┌──────────────┐
                     │                  │──→│  审计服务     │
                     │                  │   │  记录所有事件 │
                     └──────────────────┘   └──────────────┘
                             │
                             │
                     ┌──────────────────┐   ┌──────────────┐
                     │                  │──→│  监控服务     │
                     │                  │   │  统计指标     │
                     └──────────────────┘   └──────────────┘
```

#### Redis Pub/Sub vs Kafka 选择

| 维度 | Redis Pub/Sub | Kafka |
|------|-------------|-------|
| **延迟** | < 1ms | 5-20ms |
| **持久化** | 不持久化（消息发完就没了） | 持久化到磁盘 |
| **消息回放** | 不支持 | 支持（按 offset 回放） |
| **消费者组** | 不支持（每个订阅者收到全量） | 支持（消息分片到不同消费者） |
| **吞吐量** | 百万级/秒 | 百万级/秒 |
| **运维复杂度** | 低（Redis 你已经有了） | 高（需要独立集群） |
| **适用规模** | 中小规模（< 100 Worker） | 大规模（数百 Worker） |
| **推荐场景** | SSE Server 实时推送事件 | 大规模任务队列 + 事件持久化 |

**推荐起步方案**：Redis Pub/Sub 做事件总线 + Redis Streams 做任务队列。等规模大了再迁移到 Kafka。

## 2.4 State Store（状态存储）

### 为什么状态存储是长任务 Agent 的核心难题

```
问题场景:
  Agent 执行一个复杂任务，已经跑了 20 分钟，执行了 15 个步骤...
  第 16 步失败了。

  Demo 的结果: 从头再来。20 分钟白费了。
  生产的期望: 从第 16 步恢复。前 15 步的结果还在。
```

这要求 Agent 的每一步状态都被**持久化**，而不是只存在于内存中。

### 状态分层架构

```
┌────────────────────────────────────────────────────────────┐
│  Layer 1: Ephemeral State (瞬时状态)                        │
│                                                              │
│  存储: Redis / 内存                                          │
│  内容:                                                       │
│  • 当前执行步骤的临时变量                                     │
│  • LLM streaming 过程中的中间 token                          │
│  • 工具调用正在处理中的中间状态                               │
│  生命周期: 分钟级                                             │
│  访问模式: 高频读写，要求低延迟                               │
│  容错: 丢了也没关系，可以从持久层重建                         │
├────────────────────────────────────────────────────────────┤
│  Layer 2: Session State (会话状态)                           │
│                                                              │
│  存储: PostgreSQL                                            │
│  内容:                                                       │
│  • 执行图快照 (Checkpoint) — 每一步的完整状态                │
│  • 对话历史 — 用户和 Agent 的完整交互记录                    │
│  • 工具调用结果缓存 — 避免重复调用                           │
│  • 任务状态 — PENDING/RUNNING/COMPLETED/FAILED              │
│  生命周期: 天级                                               │
│  访问模式: 中频读写，要求持久化                               │
│  容错: 必须持久化，丢失 = 任务进度丢失                       │
├────────────────────────────────────────────────────────────┤
│  Layer 3: Persistent State (持久状态)                        │
│                                                              │
│  存储: PostgreSQL + 向量数据库                               │
│  内容:                                                       │
│  • 长期记忆 — 用户偏好、历史知识、行为模式                   │
│  • 审计日志 — 所有 Agent 操作的不可篡改记录                  │
│  • 用户/租户配置 — 权限、配额、偏好设置                      │
│  • 任务历史 — 已完成任务的结果和统计                         │
│  生命周期: 永久 / 按数据保留策略清理                          │
│  访问模式: 低频写，中频读                                     │
│  容错: 必须持久化且有备份                                    │
└────────────────────────────────────────────────────────────┘
```

### Checkpoint/Resume 详解

#### 什么是 Checkpoint

Checkpoint 是 Agent 执行过程中**某个时间点的完整状态快照**。通过保存 Checkpoint，可以在任意中断点恢复执行。

#### Checkpoint 数据结构

```json
{
  "checkpoint_id": "cp-456",
  "run_id": "task-123",
  "created_at": "2026-05-10T15:30:00Z",

  "execution_state": {
    "current_node": "analyze_results",
    "next_nodes": ["generate_report"],
    "completed_nodes": ["parse_intent", "search_knowledge", "call_tool_a", "call_tool_b"]
  },

  "variables": {
    "user_query": "分析 XX 技术的市场前景",
    "search_results": [
      {"source": "doc-1", "content": "...", "relevance": 0.95},
      {"source": "doc-2", "content": "...", "relevance": 0.87}
    ],
    "tool_a_result": {"status": "success", "data": {...}},
    "tool_b_result": {"status": "success", "data": {...}}
  },

  "conversation_state": {
    "messages": [
      {"role": "system", "content": "..."},
      {"role": "user", "content": "..."},
      {"role": "assistant", "content": "...", "tool_calls": [...]},
      {"role": "tool", "content": "..."}
    ],
    "token_count": 15000
  },

  "metadata": {
    "total_tokens_used": 15000,
    "total_elapsed_seconds": 330,
    "step_count": 4,
    "retry_count": 0,
    "cost_usd": 0.30
  }
}
```

#### Checkpoint 触发时机

```
什么时候保存 Checkpoint?

  □ 每个执行节点完成后（推荐）
    → 任何一步失败都可以从上一步恢复
    → 代价: 频繁的 DB 写入

  □ 每个关键里程碑完成后
    → 只在重要节点保存，减少 DB 写入
    → 代价: 可能需要回退更多步骤

  □ 定时保存（如每 30 秒）
    → 适用于连续执行的长步骤
    → 代价: Checkpoint 不一定在安全点
```

#### 恢复策略

```
恢复策略选择:

策略 1: 精确恢复（推荐）
─────────────────────────
从失败的节点重新执行
前提: 每个节点是幂等的（重复执行结果一样）
适用: 大多数场景

  Checkpoint 指向 Step 4 (已完成)
  → 从 Step 5 开始重新执行
  → Step 4 的结果从 Checkpoint 恢复

策略 2: 步骤回退
─────────────────────────
回退到上一个安全点重新执行
适用: 失败节点的上游结果可能有问题

  Step 4 失败，但怀疑 Step 3 的结果有问题
  → 回退到 Step 2 的 Checkpoint
  → 从 Step 3 重新执行

策略 3: 降级恢复
─────────────────────────
跳过失败步骤，用简化策略继续
适用: 失败步骤不是关键路径

  Step 4 (高级分析) 失败
  → 跳过，用 Step 3 的原始结果继续
  → 在最终输出中标注"高级分析未完成"
```

#### 推荐工具

| 工具 | 特点 | 适用场景 |
|------|------|---------|
| **LangGraph Checkpointer** | 与 LangGraph 深度集成，开箱即用 | 使用 LangGraph 的项目 |
| **Temporal** | 通用的工作流引擎，强状态管理 | 需要跨服务状态管理 |
| **自建** | 基于 PostgreSQL 的 Checkpoint 表 | 有特殊需求 |

### 对话历史的存储策略

```
问题: 对话历史随着轮数增长会越来越大
  10 轮对话 ≈ 5000-10000 tokens
  50 轮对话 ≈ 50000-100000 tokens
  100 轮对话 ≈ 可能超过 Context Window

解决: 分层存储 + 按需加载

全量历史 → PostgreSQL (永久存储)
                 ↓
    最近 N 轮 → Redis (快速访问)
                 ↓
    当前上下文 → Prompt (LLM 可见)

当对话超过 Prompt 容量时:
  1. 自动摘要压缩早期对话
  2. 保留关键决策点和结论
  3. 丢弃冗余的推理过程
```
