## 设计原则

### 渐进式改造

不要试图一步到位。按以下原则排序改造优先级：

```
优先级排序逻辑:

  1. 先止血: 防止系统崩溃的最基本保障（超时、限流、fallback）
  2. 再可观测: 能看到问题才能解决问题（日志、追踪）
  3. 再安全: 防止被攻击和数据泄露（Guard、沙箱）
  4. 再扩展: 支撑更多用户和更复杂任务（异步、多租户）
  5. 最后优化: 降本增效（缓存、A/B 测试）
```

### 前置条件

在开始改造之前，确认系统具备：
- 可运行的 Agent Demo（能完成基本任务）
- 代码版本控制（Git）
- 基本的部署流程（能部署到服务器）
- 至少一个 LLM Provider 的 API 访问

## Phase 1: 紧急基础 (1-2 周)

**目标**：系统不再轻易崩溃，有最基本的生产保障。

### 1.1 LLM Gateway + 多 Provider 支持

**目标**：LLM Provider 宕机时系统仍可用。

**具体行动**：
1. 引入 LiteLLM 作为统一调用层（或自建薄封装）
2. 配置至少 2 个 Provider（如 OpenAI + Anthropic）
3. 配置 Fallback 链：Provider A 超时/5xx → 自动切换 Provider B
4. 为每次调用记录 Provider、模型、Token 数

**验证方法**：
- 手动模拟 Provider A 不可用（配置错误的 API Key）→ 确认自动切换到 Provider B
- 检查日志中有 Provider 和 Token 记录

**预计工作量**：2-3 天

**注意事项**：
- 不同 Provider 的 API 格式略有差异，LiteLLM 帮你抹平
- Fallback 超时设置不要太长（建议 10-15s），否则用户等太久

### 1.2 基础结构化日志 + Request ID

**目标**：出问题时能追溯到具体请求的完整执行链路。

**具体行动**：
1. 每个请求生成唯一 `request_id`（UUID）
2. 所有日志输出为 JSON 格式，包含 `request_id`、`timestamp`、`event_type`
3. 关键事件必须记录：LLM 调用（输入摘要/输出摘要/Token/耗时）、工具调用（参数/结果/耗时）、错误
4. 日志写入文件或 stdout（后续接入日志系统）

**验证方法**：
- 执行一个任务 → 用 `request_id` grep 日志 → 能看到完整的执行链路
- 确认每条日志都是有效 JSON

**预计工作量**：1-2 天

### 1.3 超时控制 + 步数限制

**目标**：Agent 不会无限运行，不会消耗无限资源。

**具体行动**：
1. 每次 LLM 调用设置超时：30s（简单请求）/ 60s（复杂请求）
2. 每次工具调用设置超时：按工具类型配置（搜索 10s、API 30s）
3. 总任务超时：10min（默认），可按场景配置
4. 最大执行步数：20 步（默认）

**验证方法**：
- 构造一个会超时的场景（如调用不存在的 API）→ 确认在超时后优雅退出
- 构造一个会循环的场景 → 确认在 20 步后停止

**预计工作量**：1 天

### 1.4 循环检测

**目标**：Agent 不会陷入无限循环消耗 Token。

**具体行动**：
1. 实现滑动窗口循环检测（窗口大小 10，阈值 3）
2. 对工具调用做参数 hash，检测相同工具+相同参数的重复调用
3. 检测到循环后：注入提示让 Agent 换策略 → 仍循环则强制终止

**验证方法**：
- 构造一个 Agent 会循环搜索的场景 → 确认在 3 次重复后触发检测
- 确认触发后 Agent 尝试换策略或优雅终止

**预计工作量**：1 天

## Phase 2: 核心加固 (2-4 周)

**目标**：系统可观测、可恢复、基本安全。

### 2.1 异步任务执行 + 状态持久化

**目标**：长任务不阻塞 HTTP 请求，进程崩溃不丢失进度。

**具体行动**：
1. 引入 Redis 作为任务队列（Redis Streams 或 Bull/BullMQ）
2. 拆分为 API Server（接收请求、返回 task_id）+ Worker（执行 Agent）
3. 实现 Checkpoint：每步完成后将状态写入 PostgreSQL
4. 实现恢复：Worker 启动时检查未完成任务，从 Checkpoint 恢复

**验证方法**：
- 提交长任务 → 中途杀掉 Worker → 重启 Worker → 确认从中断点恢复
- 确认 API 请求立即返回 task_id，不阻塞

**预计工作量**：5-7 天

**注意事项**：
- 如果用 LangGraph，它内置 Checkpointer（PostgresSaver/RedisSaver）
- 如果自建，Checkpoint 表至少包含：run_id, step, state_json, created_at

### 2.2 分布式追踪

**目标**：能在仪表盘上看到每个任务的完整执行链路。

**具体行动**：
1. 选择工具：LangSmith（LangChain 生态）或 LangFuse（开源通用）
2. 集成 SDK，为每个 LLM 调用和工具调用自动生成 Span
3. 配置仪表盘：任务完成率、平均耗时、Token 消耗趋势
4. 配置基础告警：任务完成率 < 90%、单任务成本 > 阈值

**验证方法**：
- 执行一个任务 → 在仪表盘上看到完整的 Trace（每步的输入/输出/耗时）
- 触发一个告警条件 → 确认收到通知

**预计工作量**：3-5 天

### 2.3 Input Guard

**目标**：基本的 Prompt 注入防御。

**具体行动**：
1. 实现规则引擎层：检测常见注入模式（"ignore previous", "system:", 等）
2. 实现 Prompt 隔离：用标签分隔用户输入和系统指令
3. 可选：接入 LLM-as-Judge 做精确判断（成本较高，可后续加）

**验证方法**：
- 发送已知的 Prompt 注入样本 → 确认被拦截
- 发送正常请求 → 确认不被误拦

**预计工作量**：3-4 天

### 2.4 基础 Golden Dataset + 回归测试

**目标**：Prompt/模型变更后能自动检测质量退化。

**具体行动**：
1. 构建 20-50 个核心场景的测试用例（覆盖：简单查询、多步任务、安全测试、边界条件）
2. 实现自动化运行脚本：遍历测试用例 → 执行 → 对比预期 → 生成报告
3. 集成到 CI：Prompt 文件变更时自动触发回归测试

**验证方法**：
- 故意改坏一个 Prompt → 运行回归测试 → 确认检测到退化
- 正常变更 → 确认测试通过

**预计工作量**：5-7 天

## Phase 3: 企业级 (1-2 月)

**目标**：满足企业级要求——多租户、安全合规、人机协作。

### 3.1 完整的三层记忆系统

**目标**：Agent 能记住用户偏好，长任务不丢失上下文。

**具体行动**：
1. 工作记忆：实现 Context Window 管理（滑动窗口 + 关键信息提取）
2. 短期记忆：实现对话摘要压缩（超过 N 轮时自动摘要）
3. 长期记忆：实现用户偏好/知识积累的存储和语义检索

**验证方法**：
- 长对话（50+ 轮）→ 确认 Agent 仍记得早期关键信息
- 新会话 → 确认 Agent 能检索到上次会话的用户偏好

**预计工作量**：2-3 周

### 3.2 工具注册中心 + 沙箱执行

**目标**：工具执行安全可控，新工具可以灰度上线。

**具体行动**：
1. 实现工具注册表（JSON Schema 定义每个工具的参数、权限、限流）
2. 实现 Docker 沙箱执行（高风险工具在容器中运行）
3. 实现工具版本管理（新版本灰度 10% → 50% → 100%）

**验证方法**：
- 工具参数不合法 → 确认被 Schema 校验拦截
- 工具尝试访问禁止的网络/文件 → 确认被沙箱阻止

**预计工作量**：2 周

### 3.3 Human-in-the-Loop 审批流

**目标**：高风险操作有人工把关。

**具体行动**：
1. 定义风险等级分类（[低]/[中]/[高]/[禁止]）
2. 实现审批工作流（暂停 → 通知 → 审批/拒绝 → 恢复/终止）
3. 实现通知机制（邮件/Slack/站内消息）
4. 实现超时策略（审批超时后的自动处理）

**验证方法**：
- Agent 执行到高风险操作 → 确认暂停并发送通知
- 审批通过 → 确认 Agent 恢复执行
- 审批超时 → 确认执行超时策略

**预计工作量**：1-2 周

### 3.4 成本控制 + 多租户

**目标**：不同租户数据隔离，成本可控。

**具体行动**：
1. 实现 Token 计量：每次 LLM 调用记录消耗，归因到租户
2. 实现预算上限：租户/任务级别的 Token 预算，超了降级或拒绝
3. 实现数据隔离：所有数据查询强制附加 tenant_id 过滤
4. 实现资源配额：每租户的并发任务数、每日 Token 上限

**验证方法**：
- 租户 A 的 Agent 尝试访问租户 B 的数据 → 确认被拦截
- 任务 Token 消耗超过预算 → 确认降级或终止

**预计工作量**：2 周

## Phase 4: 持续优化

**目标**：质量持续提升，成本持续优化。

### 4.1 红队测试体系

**具体行动**：
1. 建立攻击样本库（Prompt 注入、越狱、数据泄露等 100+ 样本）
2. 每月执行一次全量红队测试
3. 每次重大变更前执行针对性红队测试
4. 发现新攻击面 → 更新 Guard 规则 → 加入回归测试

### 4.2 在线评估 + 自动化质量监控

**具体行动**：
1. 部署 LLM-as-Judge：每 100 个请求抽样 5 个做质量评估
2. 建立质量趋势仪表盘：准确率/完整性/安全性的 7 天趋势
3. 配置异常检测：质量指标突然下降 > 10% → 自动告警

### 4.3 语义缓存

**具体行动**：
1. 对高频场景启用语义缓存（相似度 > 0.95 命中）
2. 配置 TTL：知识类 1h，时效类 5min
3. 监控缓存命中率和节省的成本

### 4.4 A/B 测试框架

**具体行动**：
1. 实现流量分割：按用户/租户/随机分配到不同 Prompt 版本
2. 实现指标对比：新旧版本的质量/成本/延迟对比
3. 实现自动决策：新版本指标不退化 → 自动扩大流量

## 完整自检清单

### 基础设施 (Infrastructure)

| # | 检查项 | 怎么验证 | 达标标准 |
|---|--------|---------|---------|
| 1 | LLM 调用有统一的 Gateway 抽象层 | 业务代码中无直接 SDK 调用 | 所有 LLM 调用通过 Gateway |
| 2 | 支持多 Provider fallback | 模拟 Provider A 宕机 | 自动切换到 Provider B，用户无感 |
| 3 | 有请求级 Token 计量 | 查看日志/数据库 | 每次调用都有 token 记录 |
| 4 | 有成本归因（按租户/场景） | 查看成本报表 | 能按维度查看成本分布 |
| 5 | RAG 使用混合检索 | 测试精确关键词查询 | 向量+BM25 都能命中 |
| 6 | 任务通过消息队列异步执行 | API 请求立即返回 | 响应时间 < 1s |
| 7 | 状态有 Checkpoint 能力 | 中途杀进程后恢复 | 从中断点继续，不从头 |
| 8 | 有任务优先级队列 | 提交高优先级任务 | 高优先级先执行 |
| 9 | 有死信队列 | 制造失败任务 | 失败任务进入死信，可查看 |
| 10 | 知识库支持增量更新 | 新增文档 | 无需全量重建索引 |

### 平台服务 (Platform Services)

| # | 检查项 | 怎么验证 | 达标标准 |
|---|--------|---------|---------|
| 1 | 所有日志结构化（JSON） | grep 日志文件 | 每条都是有效 JSON |
| 2 | 有 Request ID 串联 | 用 ID 搜索 | 能找到完整执行链路 |
| 3 | 有分布式追踪 | 查看追踪仪表盘 | 能看到每步耗时和结果 |

| 6 | 工具执行在沙箱中 | 工具尝试越权访问 | 被沙箱阻止 |
| 7 | 有完整审计日志 | 查看审计表 | 所有操作可追溯 |
| 8 | Prompt 有版本管理 | 查看 Prompt 历史 | 能回滚到任意版本 |
| 9 | 有 Feature Flag | 灰度新功能 | 能按比例分流 |
| 10 | 密钥不在代码中 | grep 代码库 | 无硬编码密钥 |

### Agent 运行时 (Agent Runtime)

| # | 检查项 | 怎么验证 | 达标标准 |
|---|--------|---------|---------|
| 1 | 有循环检测 | 构造循环场景 | 3 次重复后触发 |
| 2 | 有步数限制 | 构造长任务 | 超过限制后优雅终止 |
| 3 | 有超时控制（每步+总任务） | 构造超时场景 | 超时后不挂起 |
| 4 | 工具调用有参数验证 | 传入非法参数 | 被 Schema 校验拦截 |

### SSE 与传输层 (Transport)

| # | 检查项 | 怎么验证 | 达标标准 |
|---|--------|---------|---------|
| 1 | Agent 状态不在 SSE 连接中 | 重启 SSE Server | Agent 状态不丢失 |
| 2 | 支持 Last-Event-ID 断线重连 | 断开网络后恢复 | 从断点继续接收 |
| 3 | 事件带 sequence ID | 查看 SSE 事件流 | 每个事件有递增 ID |
| 4 | 多实例用 Pub/Sub 路由事件 | 部署 2+ SSE Server | 事件正确路由 |
| 5 | 有心跳保活 | 监控 SSE 连接 | 每 15-30s 有心跳 |
| 6 | 有背压控制 | 模拟慢客户端 | Server 内存不溢出 |
| 7 | SSE 使用 HTTPS + 认证 | 无 Token 访问 | 被拒绝 |
| 8 | 有连接数监控 | 查看监控 | 能看到活跃连接数 |

| # | 检查项 | 怎么验证 | 达标标准 |
|---|--------|---------|---------|

| 2 | 支持任务取消 | 取消运行中任务 | 优雅终止，不丢数据 |
| 3 | 高风险操作有人工审批 | 触发高风险操作 | 暂停等待审批 |
| 4 | 有 Golden Dataset | 查看测试用例 | 20+ 核心场景覆盖 |
| 5 | 有回归测试自动化 | 改 Prompt 后 | CI 自动运行测试 |

| 7 | 支持多租户隔离 | 跨租户访问 | 被拦截 |
| 8 | 有用户反馈收集 | 用户评价 | 反馈被记录 |

## 常见决策指南

### Redis vs Kafka？

| 维度 | 选 Redis | 选 Kafka |
|------|---------|---------|
| 团队规模 | < 10 人 | > 10 人 |
| 日任务量 | < 10 万 | > 10 万 |
| 消息持久化需求 | 不强（丢几条可接受） | 强（一条都不能丢） |
| 消息回放需求 | 不需要 | 需要（审计/调试） |
| 运维能力 | 已有 Redis | 有 Kafka 运维经验 |
| **推荐起步** | **Redis Streams** | 等规模大了再迁移 |

### LangGraph vs Temporal？

| 维度 | 选 LangGraph | 选 Temporal |
|------|-------------|------------|
| 语言 | Python 项目 | 多语言项目 |
| Agent 框架 | 用 LangChain 生态 | 不用 LangChain |
| 编排复杂度 | Agent 内部编排 | 跨服务编排 |
| 状态管理 | 内置 Checkpointer | 内置强一致性状态 |
| 学习曲线 | 低（Python 原生） | 中（需要理解 Workflow 概念） |
| **推荐** | **大多数 Agent 项目** | 需要跨服务编排时 |

### 需要多 Agent 吗？

```
决策树:

  你的任务能被一个 Agent + 好工具解决吗？
    ├─ 是 → 不需要多 Agent（大多数情况）
    └─ 否 → 任务需要不同领域的专业知识吗？
              ├─ 是 → 考虑 Supervisor 模式
              └─ 否 → 任务需要多视角验证吗？
                        ├─ 是 → 考虑 MoA 模式
                        └─ 否 → 可能还是单 Agent + 更好的工具
```

**经验法则**：先用单 Agent + 强编排，等真正遇到瓶颈再拆。过早引入多 Agent 会导致成本爆炸和调试困难。

### SSE vs WebSocket？

| 维度 | 选 SSE | 选 WebSocket |
|------|--------|-------------|
| 通信方向 | 主要是服务端→客户端 | 需要频繁双向通信 |
| Agent 场景 | 流式输出推送（主流） | 实时协作 Agent |
| 实现复杂度 | 低（HTTP 原生） | 中（需要额外协议） |
| 断线恢复 | 内置 Last-Event-ID | 需自建 |
| **推荐** | **绝大多数 Agent 场景** | 极少数需要实时双向的场景 |

### 自建 LLM Gateway vs LiteLLM？

| 维度 | 选 LiteLLM | 选自建 |
|------|-----------|--------|
| 团队规模 | 任何规模 | 有专人维护 |
| Provider 数量 | 多（3+） | 少（1-2） |
| 定制需求 | 标准需求 | 有特殊路由/计费逻辑 |
| 维护成本 | 低（社区维护） | 高（自己维护） |
| **推荐** | **先用 LiteLLM 起步** | 等有特殊需求再自建 |
