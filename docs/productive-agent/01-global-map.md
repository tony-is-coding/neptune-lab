# 01 - 全局地图：企业级 Agent 系统全景

## 1. 什么是「生产级 AI Agent 系统」

在讨论 Demo 到生产的差距之前，我们需要先明确：**生产级 Agent 系统到底意味着什么？**

### 1.1 定义

生产级 AI Agent 系统是一个**能长时间、高可靠地自主执行复杂任务的 AI 应用系统**。它不只是「调用 LLM + 返回结果」，而是一个完整的软件工程系统——有自己的基础设施、运行时、监控、安全机制和运维体系。

### 1.2 核心特征

一个生产级 Agent 系统必须同时具备以下五个特征：

| 特征 | 含义 | 缺失时的后果 |
|------|------|------------|
| **可靠性 (Reliability)** | 系统在故障、异常输入、网络中断等情况下仍能产生可接受的结果 | 一点小问题就全盘崩溃，用户完全不可用 |
| **可观测性 (Observability)** | 系统的每一步执行都能被追踪、分析和回溯 | 出了问题无从排查，只能「重启试试」 |
| **安全性 (Security)** | 系统能抵御恶意输入、防止数据泄露、控制执行范围 | 被 Prompt 注入攻击、敏感数据外泄、工具被滥用 |
| **可扩展性 (Scalability)** | 系统能通过水平扩展应对增长的负载 | 用户一多就卡死，任务一长就超时 |
| **可运维性 (Operability)** | 系统能被持续部署、配置、监控和迭代 | 任何改动都需要停机，线上问题无法快速修复 |

### 1.3 与传统软件系统的本质区别

Agent 系统不是普通的 Web 服务。理解这个区别是设计生产级架构的前提：

| 维度 | 传统 Web 服务 | Agent 系统 |
|------|-------------|-----------|
| **决策主体** | 代码逻辑（确定性） | LLM（概率性） |
| **执行路径** | 预定义的路由和流程 | LLM 动态决定，每次可能不同 |
| **失败模式** | 主要是基础设施故障（网络、数据库） | 除了基础设施故障，还有 LLM 幻觉、推理错误、工具调用失败、循环决策 |
| **延迟特征** | 毫秒~秒级，相对稳定 | 秒~分钟级，高度不确定（取决于 LLM 推理步骤数） |
| **成本模型** | 主要是计算资源 | **LLM Token 调用成本可能超过计算资源成本** |
| **质量保证** | 单元测试 + 集成测试覆盖 | 需要评估框架（Eval），因为输出是非确定性的 |
| **调试难度** | 断点 + 日志 | 需要完整的推理链追踪（Prompt → 思考 → 决策 → 行动 → 结果） |

**核心洞察：Agent 系统是一个「会思考的分布式系统」。每一步「思考」都可能出错，而且出错的模式是开放式的——你无法枚举所有可能的错误路径。这就是为什么 Demo 到生产的差距如此之大。**

## 2. Demo 级 vs 生产级：架构对比

### 2.1 Demo 级 Agent 的典型架构

```
┌──────────────────────────────────────────┐
│            Demo 级 Agent                  │
│                                          │
│  用户请求                                 │
│    ↓                                     │
│  直接调用 LLM API (openai.chat.completions.create) │
│    ↓                                     │
│  解析 LLM 输出                            │
│    ↓ (如果有 tool_calls)                  │
│  直接执行工具函数 (本地进程内)             │
│    ↓                                     │
│  把工具结果拼回 messages                   │
│    ↓                                     │
│  再次调用 LLM                             │
│    ↓                                     │
│  ...循环直到 LLM 不再调用工具...           │
│    ↓                                     │
│  返回最终结果                              │
│                                          │
│  特征:                                    │
│  • 全部状态在内存 (messages 列表)          │
│  • 同步阻塞执行                           │
│  • 单 LLM Provider                       │
│  • 无超时控制                             │
│  • 无错误恢复                             │
│  • 无监控和日志                            │
│  • 无安全防护                             │
│  • 进程挂了 = 一切丢失                    │
└──────────────────────────────────────────┘
```

**Demo 级系统的隐含假设**：
1. LLM 永远可用且响应及时
2. LLM 永远做出正确的决策
3. 工具调用永远成功
4. 执行过程很快就能完成
5. 只有一个用户在使用
6. 输入都是善意的
7. 进程不会崩溃

这些假设在 Demo 演示中成立，在生产环境中**每一个都会被打破**。

│  └──────────────┘ └──────────┘ └──────────┘ └────────────────┘  │

### 2.3 四层架构的职责划分

| 层级 | 职责 | 核心问题 | Demo 中通常的状态 |
|------|------|---------|-----------------|
| **Infrastructure** | 提供底层能力：LLM 访问、数据存储、消息传递 | 「怎么让 LLM 调用永远可用？」「数据存在哪里？」 | 直连 API，全在内存 |
| **Platform Services** | 提供横切关注点：监控、安全、状态、配置 | 「出问题了能查到吗？」「Agent 被攻击了怎么办？」 | 完全缺失 |
| **Agent Runtime** | Agent 的核心执行逻辑：思考、记忆、行动、防护 | 「Agent 怎么可靠地执行复杂任务？」「怎么防止失控？」 | 简单的 while 循环 |
| **Application** | 面向用户和外部系统的接口 | 「用户怎么使用和管理 Agent？」「怎么保证质量？」 | 基础的请求-响应 |

### 2.4 四大支柱如何融入每一层

四大支柱（可靠性、可观测性、安全性、可扩展性）不是某一层的专属职责，而是**每一层都需要考虑的横切关注点**：

| 支柱 \ 层 | Infrastructure | Platform Services | Agent Runtime | Application |
|----------|---------------|-------------------|--------------|-------------|
| **可靠性** | LLM Gateway fallback、消息持久化 | 状态 Checkpoint、配置版本化 | 循环检测、超时控制、重试策略 | 任务重试、人工兜底 |
| **可观测性** | LLM 调用日志、Token 计量 | 分布式追踪、指标仪表盘 | 决策链记录、工具调用审计 | 用户反馈收集、Eval 结果 |
| **安全性** | API Key 管理、网络隔离 | 输入/输出 Guard、数据隔离 | 工具沙箱、执行边界控制 | 权限管理、审计日志 |
| **可扩展性** | 消息队列、向量DB 分片 | 无状态服务、水平扩展 | 异步执行、状态外部化 | 多租户、资源配额 |

## 3. 完整差距矩阵：Demo vs 生产

### 3.1 核心维度对比

| 维度           | Demo 做法                         | 生产做法                                                           | 为什么必须改                                          | 不改的后果                                 |
| ------------ | ------------------------------- | -------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------- |
| **LLM 调用**   | 直连单一 SDK（如 `openai`），单 Provider | Gateway 统一抽象 + 多 Provider fallback + 限流 + 成本追踪                 | LLM Provider 会宕机、限流、涨价                          | Provider 宕机 → 全系统不可用；无成本追踪 → 账单失控     |
| **执行模式**     | 同步阻塞，单个 HTTP 请求内完成全部执行          | 异步任务提交 + 消息队列分发 + Worker 异步消费 + SSE 流式推送                       | 复杂任务可能执行数分钟到数小时                                 | 超时断开、用户无法等待、资源浪费                      |
| **流程编排**     | 手写 if-else 链或简单的顺序调用            | DAG 引擎（LangGraph/Temporal），支持条件分支、并行、子图、状态持久化                  | 复杂任务的执行路径是动态的，硬编码无法应对                           | 流程变更需改代码重新部署，无法处理异常分支                 |
| **Agent 编排** | 单 Agent 打天下                     | 单 Agent 强编排为主 + 按需引入 Supervisor 多 Agent                        | 单 Agent 靠好的工具和编排足以应对大多数场景；多 Agent 有选择性地用        | 多 Agent 滥用 → 成本爆炸、调试困难、幻觉叠加           |
| **错误处理**     | try-catch 包一下，或完全不管             | 熔断（Circuit Breaker）、降级（Fallback）、分级重试（Retry with backoff）、优雅退出 | LLM 调用、工具执行、网络请求都可能失败                           | 一个工具失败 → 整个任务失败 → 用户白等                |
| **记忆系统**     | 所有信息都在 messages 列表里（Prompt 内）   | 三层记忆架构：工作记忆（Prompt 内）+ 短期记忆（会话级）+ 长期记忆（持久化）                    | Context Window 有限（128K tokens），长任务产生的中间结果远超窗口容量 | 长任务丢失上下文 → Agent 忘记之前做了什么 → 重复工作或错误决策 |
| **可观测性**     | `print()` 或 `console.log()`     | 结构化日志 + 分布式追踪（Span-based）+ 指标仪表盘 + 告警                          | Agent 执行路径不确定，出问题时需要完整回溯                        | 出了问题无法排查，「黑盒」运行，只能「重启试试」              |
| **安全防护**     | 无任何防护                           | 输入防御（Prompt 注入检测）+ 执行沙箱 + 输出审核（PII/合规）+ 审计日志 + 数据隔离            | Agent 会「思考」并执行操作，攻击者可以通过输入影响 Agent 的决策          | 被注入恶意指令 → Agent 执行危险操作 → 数据泄露/破坏      |
| **水平扩展**     | 单进程，所有计算和状态在一个进程中               | 无状态 Worker（从队列领取任务）+ 外部状态存储 + SSE Server 集群                    | 单进程能处理的并发和吞吐有限                                  | 用户量增长 → 系统崩溃                          |
| **多租户**      | 无概念，全局共享                        | 租户级数据隔离 + 资源配额（Token/并发/存储上限）+ 租户级配置                           | 企业场景中不同组织的数据不能交叉                                | A 公司的数据被 B 公司的 Agent 看到 → 严重合规事故      |
| **成本控制**     | 完全不关心，看月度账单                     | 请求级 Token 计量 + 成本归因（按租户/场景/用户）+ 预算上限 + 优化策略（缓存、模型路由）           | LLM 调用成本是变量成本，随使用量线性增长                          | 恶意用户或异常请求 → 单日成本失控                    |
| **合规性**      | 无考虑                             | 数据留存策略 + 内容审核 + 不可篡改审计日志 + GDPR/行业合规                           | 不同行业有不同合规要求（金融、医疗、政府）                           | 无法通过合规审计 → 无法上线                       |
| **质量保证**     | 手动测试几个案例                        | Eval 框架（Golden Dataset + 回归测试 + 红队测试 + 在线评估）                   | Agent 输出是非确定性的，传统的单元测试不够                        | 改了一行 Prompt → 线上质量退化 → 不知道变坏了         |

### 3.2 从 Demo 到生产的思维转变

差距矩阵背后，是一系列**根本性的思维转变**：

#### 转变一：从「乐观执行」到「防御性执行」

```
Demo 思维：
  "LLM 会返回正确结果，工具会执行成功，一切都会顺利"

生产思维：
  "LLM 可能返回错误结果，工具可能执行失败，网络可能断开，
   我需要在每一步都考虑失败的情况并有能力恢复"
```

**具体体现**：
- 每一步 LLM 调用都有超时和 fallback
- 每一次工具调用都有参数校验和错误处理
- 每一次决策都有合理性和安全性检查
- 整个执行过程有 Checkpoint，可以从任意点恢复

#### 转变二：从「同步即时」到「异步持久」

```
Demo 思维：
  "用户发请求 → 我同步执行完 → 返回结果 → 完事"

生产思维：
  "用户提交任务 → 任务持久化到队列 → Worker 异步执行 →
   中间状态实时推送 → 支持暂停/恢复/取消 →
   即使服务重启也不丢失进度"
```

**具体体现**：
- 任务通过消息队列异步分发
- 执行状态持久化到数据库
- SSE 流式推送中间进度
- 支持从 Checkpoint 恢复执行

#### 转变三：从「黑盒运行」到「白盒可观测」

```
Demo 思维：
  "能跑就行，出了问题我再看看"

生产思维：
  "每一步执行都有 Trace ID 串联，
   每个 LLM 调用都有输入/输出/耗时/Token 记录，
   每个工具调用都有参数/结果/成功状态，
   出问题后可以在仪表盘上完整回溯"
```

#### 转变四：从「信任输入」到「验证一切」

```
Demo 思维：
  "用户输入是善意的，LLM 输出是正确的"

生产思维：
  "用户输入可能包含 Prompt 注入，
   RAG 检索到的文档可能藏有恶意指令，
   LLM 输出可能包含幻觉或敏感信息，
   每个环节都需要验证和防护"
```

#### 转变五：从「单用户场景」到「多租户平台」

```
Demo 思维：
  "一个用户，一个进程，一套配置"

生产思维：
  "多个组织同时使用，数据严格隔离，
   不同租户有不同的配额和权限，
   系统需要按租户维度计量、计费、审计"
```

## 4. SSE 在生产环境中的关键考虑

SSE（Server-Sent Events）是当前主流 Agent 系统的客户端通信方案。但 SSE 在 Demo 和生产中的用法差距巨大。

### 4.1 SSE 的正确定位：传输层 vs 架构层

**最常见的误解：把 SSE 当成了架构的全部。**

```
错误理解：
  "用 SSE 了，所以我的系统是实时的、异步的"

正确理解：
  SSE 只是「最后一公里」——把结果从服务端推送到客户端的传输协议。
  它不解决任务分发、状态管理、Worker 调度等架构问题。
```

**正确的三层架构**：

```
┌───────────────────────────────────────────────────────────────────┐
│  Layer 1: 客户端传输层 (SSE / WebSocket)                          │
│  职责：把结果从服务端推送给客户端                                   │
│  关注点：断线重连、背压控制、心跳保活                               │
│                                                                    │
│  ┌───────────────┐     SSE 连接      ┌─────────────────────────┐ │
│  │  客户端        │ ◄───────────────  │  SSE Server (集群)      │ │
│  │  (Browser/App)│                   │  职责：维持SSE连接，     │ │
│  └───────────────┘                   │        推送事件          │ │
│                                       └────────────┬────────────┘ │
│                                                     │              │
│  Layer 2: 内部事件层 (Redis Pub/Sub / Kafka)         │              │
│  职责：在服务间传递事件，解耦 Worker 和 SSE Server     │              │
│  关注点：持久化、消费者组、offset 追踪                 │              │
│                                                     │              │
│                            ┌────────────────────────┐│              │
│                            │  Message Queue / Event ││              │
│                            │  Bus (Redis/Kafka)     ││              │
│                            └────────────┬───────────┘│              │
│                                          │            │              │
│  Layer 3: 任务分发层 (Task Queue)          │            │              │
│  职责：管理任务队列，Worker 从队列领取执行   │            │              │
│  关注点：优先级、死信队列、任务状态追踪      │            │              │
│                                          │            │              │
│                            ┌─────────────┴────────────┘             │
│                            │                                        │
│                   ┌────────┴─────────┐                             │
│                   │  Agent Worker     │                             │
│                   │  (集群)           │                             │
│                   │  职责：执行Agent   │                             │
│                   │  逻辑，发布事件    │                             │
│                   └──────────────────┘                             │
└───────────────────────────────────────────────────────────────────┘
```

### 4.2 SSE vs 其他传输方案对比

| 方案 | 方向 | 延迟 | 浏览器兼容 | 断线恢复 | 实现复杂度 | Agent 场景适用度 |
|------|------|------|-----------|---------|-----------|----------------|
| **SSE** | 单向（Server → Client） | 低（~ms） | 极好（原生支持） | 内置 `Last-Event-ID` 机制 | 低 | **最佳选择**：Agent 输出流式推送 |
| **WebSocket** | 双向 | 最低 | 好 | 需自建重连+状态恢复 | 中 | 需要客户端实时交互时（如协作编辑） |
| **Streaming gRPC** | 双向 | 最低 | 需 gRPC-Web | 需自建 | 高 | 微服务内部通信，不适合浏览器 |
| **Long Polling** | 伪双向 | 高（~s） | 极好 | 天然支持 | 极低 | 兼容性兜底，不推荐 |

**为什么 SSE 是当前主流选择**：
1. Agent 场景主要是「服务端向客户端推送结果」，单向足够
2. 浏览器原生支持，无需额外库
3. 自动重连机制（`Last-Event-ID`）开箱即用
4. 基于 HTTP，穿透代理/防火墙无障碍
5. 比 WebSocket 实现简单得多

**什么时候需要 WebSocket**：当客户端需要频繁向服务端发送实时指令（如实时协作 Agent、远程控制 Agent）时。大多数 Agent 场景不需要。

### 4.3 SSE 生产化检查清单

#### 必须实现

| 检查项 | 问题场景 | 实现方式 |
|--------|---------|---------|
| **状态外部化** | SSE Server 重启/宕机 → 连接断开 → Agent 状态不能跟着丢 | Agent 状态存 Redis/DB，SSE 连接只是「管道」，不存任何业务状态 |
| **Last-Event-ID 断线重连** | 网络抖动导致连接断开 → 客户端重连后需要知道从哪里继续 | 客户端重连时携带 `Last-Event-ID` header，SSE Server 从该 ID 之后继续推送 |
| **事件 sequence ID** | 网络不稳定可能收到重复或乱序事件 | 每个事件带递增的 `id` 字段，客户端按 ID 去重和排序 |
| **心跳保活** | Nginx/Load Balancer 的 idle timeout 通常 60s，Agent 思考时间可能更长 | 每 15-30s 发送 SSE 注释 `: keepalive\n\n`，保持连接活跃 |
| **背压控制** | Agent 产生事件太快，客户端消费太慢 → SSE Server 内存溢出 | 详见 4.4 节 |
| **HTTPS + 认证** | SSE 不支持自定义 Header，Token 如何传递 | 使用 Cookie（推荐，自动携带）或 URL Query Parameter（需 HTTPS） |

#### 多实例部署时必须

| 检查项 | 问题场景 | 实现方式 |
|--------|---------|---------|
| **Pub/Sub 跨实例事件路由** | Agent Worker 在机器 A，SSE 连接在机器 B，事件怎么从 A 到 B？ | Redis Pub/Sub 或 Kafka：Worker 发布事件 → 所有 SSE Server 订阅 → 匹配 task_id 的 Server 推送 |

#### 推荐实现

| 检查项 | 说明 |
|--------|------|
| **连接数监控** | 监控每台 SSE Server 的活跃连接数，超过阈值告警 |
| **连接数限流** | 防止恶意客户端打开大量连接耗尽资源 |
| **事件大小限制** | 单个 SSE 事件大小上限（如 64KB），防止工具返回超大结果撑爆传输 |

### 4.4 背压问题详解

#### 什么是背压（Backpressure）

背压是指**当数据的生产速度超过消费速度时，系统如何处理积压数据的机制**。

#### 为什么 SSE Server 会内存溢出

```
问题根源：生产者-消费者速度不匹配

Agent Worker (生产者)              SSE 连接 (管道)            客户端 (消费者)
  生产事件速度:                    网络带宽限制:               消费速度:
  ~100 个事件/秒                   ~50 个事件/秒               ~10 个事件/秒
  (LLM streaming token 很快)       (移动网络/弱网)             (浏览器 JS 处理)
```

**逐步过程**：

```
时间 0s:
  Worker 产生事件 → SSE Server 收到 → 尝试推给客户端
  客户端接收速度跟不上
  SSE Server 把还没推出去的事件存在内存缓冲区（socket buffer）里

时间 10s:
  Worker 又产生了 ~1000 个事件
  客户端只消费了 ~100 个
  缓冲区积累了 ~900 个事件（每个事件几 KB）

时间 60s:
  缓冲区积累了几万个事件
  占用内存可能到几百 MB

时间 10min:
  如果有 100 个这样的慢客户端同时连接
  内存: 100 × 几百MB = 几十GB → OOM (Out Of Memory)
```

**根本原因**：SSE 底层是 TCP 连接。当 TCP 发送缓冲区满时（对方消费慢），应用层写入的数据积压在内存中。

#### 事件总线能否解决背压

```
Worker ──→ Kafka ──→ SSE Server ──网络──→ 客户端
                ↑                           ↑
          这一段永不溢出               瓶颈仍然在这里!
```

**Kafka 解决了什么**：
- Worker 和 SSE Server 完全解耦：Worker 只管往 Kafka 写，不关心下游
- Kafka 把消息持久化到磁盘，缓冲能力 TB 级
- SSE Server 挂了重启后从 offset 继续消费，不丢消息
- Worker 永远不会被慢客户端拖垮

**Kafka 没有解决什么**：
- SSE Server → 客户端这段网络的传输速度仍然受限于客户端的网络和处理能力
- SSE Server 从 Kafka 消费消息后，还是要通过 SSE 推给客户端
- 如果 SSE Server 消费速度 > 推送速度，SSE Server 自己的内存还是会溢出

**结论**：事件总线把背压问题从 Worker 转移到了 SSE Server。Worker 安全了，但 SSE Server 需要自己处理背压。

#### SSE Server 端的背压策略

| 策略 | 思路 | 适用场景 | 代码示意 |
|------|------|---------|---------|
| **控制消费速率** | SSE Server 检查每连接缓冲区水位，满时暂停从 Kafka 消费 | 所有场景（推荐优先使用） | `if (buffer.watermark > threshold) { kafkaConsumer.pause(taskTopic) }` |
| **智能丢弃** | 给事件标优先级，缓冲区满时丢弃低优先级事件 | 对实时性要求高但允许丢失中间状态 | `if (buffer.full && event.priority == LOW) { drop(event) }` |
| **事件合并** | 连续的 streaming token 合并为一个事件再发送 | LLM streaming 场景 | `buffer.merge_similar(maxInterval=200ms)` |
| **断开慢客户端** | 缓冲区超过上限时主动断开，让客户端重连后从最新状态开始 | 极端场景的最后兜底 | `if (buffer.size > MAX) { res.end(); client.reconnect(); }` |

### 4.5 SSE 完整的数据流

```
用户提交任务
    ↓
API Gateway (验证、鉴权、限流)
    ↓
生成 task_id，任务入队 (Redis/Kafka Task Queue)
    ↓ 返回 task_id 给客户端
客户端建立 SSE 连接: GET /tasks/{task_id}/events
    ↓
SSE Server 注册 task_id → SSE 连接的映射
同时订阅 Redis Pub/Sub topic: task:{task_id}:events
    ↓
Agent Worker 从 Task Queue 领取任务
    ↓
Worker 开始执行 Agent 逻辑:
    ↓ (每产生一个事件)
Worker 发布事件到 Redis Pub/Sub:
    {task_id: "xxx", event_id: 42, type: "token", data: "..."}
    ↓
SSE Server 收到 Pub/Sub 消息:
    → 检查 task_id 对应的 SSE 连接
    → 检查背压（缓冲区水位）
    → 推送事件: id: 42\ndata: ...\n\n
    ↓
...Agent 继续执行...
    ↓
Worker 发布完成事件:
    {task_id: "xxx", event_id: 100, type: "complete", data: "{...}"}
    ↓
SSE Server 推送完成事件给客户端
SSE 连接关闭
清理 Pub/Sub 订阅
```

**如果中途 SSE 连接断了**：
```
客户端自动重连 (SSE 内置机制)
    ↓
携带 Last-Event-ID: 42 (最后一次收到的事件 ID)
    ↓
SSE Server 从状态存储查询 task_id=xxx 的最新状态
    ↓
从 Redis Pub/Sub 或 Kafka 重放 event_id > 42 的事件
    ↓
继续正常推送
```

**如果 SSE Server 宕机了**：
```
SSE Server A 宕机
    ↓
客户端自动重连，Load Balancer 分配到 SSE Server B
    ↓
SSE Server B 也订阅了 Redis Pub/Sub
    ↓
SSE Server B 检查 task_id 对应的缓存/DB 状态
    ↓
SSE Server B 接管 SSE 连接，继续推送
（前提：Agent 状态不在 SSE Server 的内存中，而在 Redis/DB 中）
```

## 5. 从 Demo 到生产的演进路径

不是所有改造都需要一步到位。以下是一个务实的演进顺序：

### Phase 1: 止血（1-2 周）

**目标**：系统不再轻易崩溃，有最基本的保障。

```
改造前：Agent 执行一个任务，LLM 宕机就全挂了
改造后：Agent 执行一个任务，LLM 宕机自动切 Provider，超时了有兜底

具体行动：
  □ 引入 LiteLLM 或自建薄封装，统一 LLM 调用接口
  □ 配置多 Provider fallback (OpenAI → Anthropic → Azure)
  □ 每个请求生成唯一 Request ID，写入结构化日志
  □ 每步执行超时 30s，总任务超时 10min，最大步数 20
  □ 滑动窗口检测重复工具调用（防循环）
```

### Phase 2: 加固（2-4 周）

**目标**：系统可观测、可恢复、基本安全。

```
改造前：出了问题只能看 print 输出猜原因
改造后：仪表盘上看到完整的执行链路，哪个环节慢了、失败了，一目了然

具体行动：
  □ 引入 Redis 做任务队列，Worker 异步消费
  □ LangGraph Checkpointer 做状态持久化
  □ 接入 LangSmith 或 LangFuse，自动生成 Trace
  □ 规则引擎 + LLM-as-Judge 双层 Input Guard
  □ 构建 20-50 个核心场景的 Golden Dataset
```

### Phase 3: 企业级（1-2 月）

**目标**：满足企业级要求——多租户、安全合规、人机协作。

```
改造前：只有一个用户，没有安全防护，出了问题只能人工介入
改造后：多组织安全使用，高风险操作自动审批，质量持续监控

具体行动：
  □ 实现三层记忆（工作/短期/长期），含摘要压缩
  □ 工具注册表 + Schema 校验 + Docker 沙箱执行
  □ 风险等级分类 + 审批工作流 + 通知机制
  □ Token 计量 + 租户隔离 + 资源配额
```

### Phase 4: 精益（持续）

**目标**：质量持续提升，成本持续优化。

```
具体行动：
  □ 定期红队测试，建立攻击样本库
  □ 生产环境 LLM-as-Judge 抽样评估 + 趋势仪表盘
  □ 相似请求语义缓存，降低延迟和成本
  □ Prompt/模型/策略 A/B 测试，数据驱动迭代
```

## 6. 关键反模式（Anti-patterns）

在 Demo 到生产的过程中，有一些常见的错误做法需要避免：

### 反模式一：把 SSE 当架构

```
错误：所有逻辑都在 SSE handler 里写
正确：SSE 只负责推送，Agent 执行逻辑在独立 Worker 中
```

### 反模式二：过早引入多 Agent

```
错误：一开始就设计 5 个 Agent 协作
正确：先用单 Agent + 强工具 + 好编排，等真正需要时再拆
      大多数场景下「单 Agent + 强编排」优于「多 Agent」
```

### 反模式三：在 Prompt 里放所有记忆

```
错误：把全部对话历史都塞进 Prompt
正确：分层记忆 + 摘要压缩，Prompt 里只放当前需要的最小上下文
```

### 反模式四：信任 LLM 输出

```
错误：直接把 LLM 输出返回给用户或作为工具参数
正确：每一步输出都经过验证（格式、内容、安全性）
```

### 反模式五：忽略成本

```
错误：不考虑 Token 消耗，让 Agent 无限制地调用 LLM
正确：每步有 Token 预算，总任务有成本上限，异常时自动熔断
```

### 反模式六：无状态的错误处理

```
错误：失败了从头开始重试
正确：Checkpoint 机制，从失败点恢复
```
