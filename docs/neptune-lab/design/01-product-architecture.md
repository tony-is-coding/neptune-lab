# Neptune AgentOps 产品架构设计

日期：2026-05-22

状态：产品架构设计

依据：

- `docs/strategy/neptune-agentops-platform-strategy.md`
- `docs/superpowers/specs/2026-05-22-neptune-agentops-product-architecture-design.md`

## 0. 结论

Neptune 不是聊天式智能体工具，也不是财务 SaaS。Neptune 的产品架构必须围绕一个中心命题展开：

**把企业对智能体的受控委托，变成可交付、可治理、可审计、可升级的生产事实链。**

第一阶段产品必须形成三大入口：

1. **交付台**：服务 SI / AI 交付团队，把客户项目、智能体模板、技能、数据源、试运行和验收组织成可复制交付流程。
2. **治理台**：服务客户技术治理方，让每一次智能体行为都能解释、审计、追责、控成本、看版本。
3. **关账工作台**：服务客户业务责任方，用中国 ERP 财务月结关账验证平台内核，而不是把平台改造成财务软件。

产品中心对象不是 `Conversation`，而是 `Controlled Run`。

最小生产事实链如下：

```text
客户项目
  -> 智能体版本
  -> 运行记录
  -> 运行事件 / 工具调用
  -> 成果文件 / 证据
  -> 异常发现
  -> 人工复核 / 批准 / 豁免 / 退回
  -> 审计事件
  -> 用量记录 / 成本
  -> 关账就绪报告
```

所有页面、对象、状态、按钮和空状态都必须服务这条链。不能把已有聊天界面换一个标题就称为 AgentOps 平台；也不能为了财务场景把平台内核污染成关账专用系统。

## 1. 第一性原理

企业采用智能体的本质不是“让模型回答问题”，而是“把部分执行任务委托给一个不完全确定的系统”。企业真正需要的不是更多对话，而是能回答以下问题：

- 这次智能体在什么权限下行动？
- 使用了哪个智能体、规则、模型、连接器和模板版本？
- 读取了什么数据和证据？
- 产生了什么判断、文件和异常？
- 谁复核了结果？
- 谁批准、退回或豁免？
- 出错后能否追溯？
- 版本升级后历史结果是否仍可解释？

因此 Neptune 的产品底座必须是 **受控委托协议**：

- `Run` 记录一次受控执行；
- `Evidence` 记录业务事实来源；
- `Finding` 记录智能体发现的问题；
- `Review / Approval / Waiver` 记录人的责任判断；
- `AuditEvent` 记录不可变责任事实；
- `Version` 记录运行依赖；
- `Cost` 记录资源消耗。

聊天可以存在，但只能作为试运行、运行详情或人工补充说明的交互形态，不能成为主信息架构。

## 2. 目标用户与产品责任

Neptune 必须同时服务四类角色，但不能把他们混成同一个“用户”。

| 用户 | 身份 | 核心问题 | 产品入口 | Neptune 的责任 |
| --- | --- | --- | --- | --- |
| SI / AI 交付团队 | 外部生态伙伴，或客户内部 AI 交付团队 | 如何更快、更标准、更可复制地交付企业智能体项目？ | 交付台 | 提供项目装配、模板复用、试运行、验收证据和交付资产 |
| 客户技术治理方 | 客户企业内部 AI / IT / 安全 / 架构团队 | 智能体是否可控、可审计、可追责、成本是否受控？ | 治理台 | 提供版本、运行、审计、策略、成本和权限事实 |
| 客户业务责任方 | 客户企业内部财务、运营、审计团队 | 本期业务流程能否推进？异常是否处理？证据是否充分？ | 关账工作台 | 提供业务流程、证据、异常、复核和报告，不替客户承担最终业务判断 |
| 经济买方 | CIO、CDO、财务共享中心负责人、数字化负责人 | 投入是否降低交付风险、治理成本和业务风险？ | 汇总视图 / 报告 | 用可见的交付效率、治理闭环和业务结果证明价值 |

战略取舍：

**卖给交付团队，用企业平台标准设计，用业务工作台证明价值。**

含义：

- 第一销售楔子面向交付团队，因为他们最痛的是项目不可复制、验收不标准、客户现场成本高。
- 第一架构标准面向客户技术治理方，因为企业智能体进入生产环境必须满足权限、审计、版本和数据边界。
- 第一业务验证面向财务关账，因为该场景能逼出证据、复核、审批、报告和历史追溯。

## 3. 产品分层

```text
┌──────────────────────────────────────────────────────────────┐
│                         三大产品入口                         │
│  交付台：项目装配 / 模板 / 技能 / 试运行 / 验收               │
│  治理台：运行 / 审计 / 版本 / 策略 / 成本                     │
│  关账工作台：期间 / 检查 / 异常 / 证据 / 复核 / 报告          │
└───────────────────────────────▲──────────────────────────────┘
                                │ 用户任务与责任链
┌───────────────────────────────┴──────────────────────────────┐
│                        Solution Pack                         │
│  中国 ERP 财务月结关账：业务对象、规则模板、证据类型、报告模板 │
│  目标：用高约束业务场景验证平台内核，不把平台做成财务 SaaS     │
└───────────────────────────────▲──────────────────────────────┘
                                │ 行业语义映射为平台事实
┌───────────────────────────────┴──────────────────────────────┐
│                    AgentOps Platform Core                     │
│  Project / AgentVersion / Connector / Run / Artifact          │
│  Evidence / Finding / Policy / Review / Audit / Eval / Cost   │
│  目标：沉淀跨行业可复用的企业智能体生产治理机制                 │
└───────────────────────────────▲──────────────────────────────┘
                                │ 调用通用执行能力
┌───────────────────────────────┴──────────────────────────────┐
│                    Neptune Runtime Kernel                     │
│  LLM / tools / MCP / streaming / trace / artifact hooks        │
│  目标：执行通用智能体 runtime，不理解财务、ERP、关账业务语义      │
└──────────────────────────────────────────────────────────────┘
```

产品设计必须遵守两条边界：

- **业务语义上浮**：财务、ERP、关账、凭证、科目余额表、报告模板属于 Solution Pack 和产品服务层。
- **运行时通用**：`neptune-engine` 只提供模型、工具、MCP、streaming、trace、artifact hook 等通用执行能力。

## 4. 三大产品入口

### 4.1 交付台

交付台面向 SI / AI 交付团队。它回答的问题是：

**我如何把一个客户智能体项目标准化交付出来，并证明它已经可以验收？**

核心对象：

- 客户项目；
- 智能体模板；
- 智能体版本；
- 技能；
- 数据源 / 连接器；
- 试运行；
- 成果文件；
- 验收记录。

核心页面：

| 页面 | 用户任务 | 必备信息 |
| --- | --- | --- |
| 交付概览 | 查看客户项目、最近运行、待处理配置、验收状态 | 项目状态、失败运行、缺失配置、验收进度 |
| 智能体模板 | 配置可复用智能体 | 模型、提示词、工具、技能、知识文件、当前版本、最近运行 |
| 技能目录 | 管理可复用能力 | 技能版本、绑定智能体、启停状态、使用情况 |
| 运行调试 | 发起试运行并查看过程 | 输入、流式输出、工具调用、成果文件、错误详情 |

关键交互：

- 新建客户项目；
- 新建智能体模板；
- 绑定技能；
- 上传知识文件；
- 绑定数据源；
- 发起试运行；
- 查看运行详情；
- 复制为新版本；
- 生成验收记录。

交付台不能做成“聊天首页”。交付团队可以使用对话式输入调试 Agent，但产品主语必须是客户项目、模板、版本、运行和验收。

### 4.2 治理台

治理台面向客户技术治理方。它回答的问题是：

**这次智能体行为是否可解释、可审计、可追责、成本是否受控？**

第一阶段治理台以只读追溯为主，不建设复杂运维控制面。

核心对象：

- 运行记录；
- 运行事件；
- 工具调用；
- 智能体版本；
- 策略决策；
- 审计事件；
- 用量记录；
- 成本概览。

核心页面：

| 页面 | 用户任务 | 必备信息 |
| --- | --- | --- |
| 运行记录 | 追溯每一次受控执行 | 状态、智能体版本、模型、发起人、耗时、请求编号、成本 |
| 审计事件 | 查看不可变责任事实 | 时间、操作、资源、执行人、结果、关联运行、请求编号 |
| 智能体版本 | 理解历史运行依赖 | 版本号、hash、创建人、配置摘要、关联运行 |
| 成本概览 | 看用量与成本归因 | 租户、项目、智能体、模型、输入输出 token、费用 |
| 策略决策 | 查看权限和数据边界判断 | 工具、MCP、路径、模型、数据出域、允许/拒绝原因 |

关键交互：

- 筛选失败运行；
- 查看运行详情；
- 查看审计链；
- 查看关联会话；
- 查看智能体版本；
- 导出审计记录；
- 查看策略拒绝原因；
- 查看成本归因。

治理台不展示“模型很聪明”。它只展示生产事实：谁做了什么、依赖什么版本、访问什么资源、产生什么结果、谁承担责任。

### 4.3 关账工作台

关账工作台面向客户业务责任方。它回答的问题是：

**本期是否具备关账条件？哪些异常阻塞关账？证据是否足够？谁负责复核和批准？**

核心对象：

- 关账工作区；
- 会计期间；
- 检查清单；
- 控制规则；
- 证据；
- 异常发现；
- 负责人；
- 复核；
- 批准 / 退回 / 豁免；
- 关账就绪报告。

核心页面：

| 页面 | 用户任务 | 必备信息 |
| --- | --- | --- |
| 期间总览 | 判断本期关账准备状态 | 账套、期间、通过率、高风险异常、待复核数、报告状态 |
| 检查清单 | 查看控制项执行状态 | 控制项、严重性、状态、负责人、复核人、关联运行 |
| 异常发现 | 处理智能体发现的问题 | 异常描述、影响范围、证据、建议、状态、责任人 |
| 证据中心 | 查证业务事实来源 | 凭证、余额表、辅助账、银行回单、发票、审批流、CSV/Excel |
| 复核队列 | 完成人工责任判断 | 待复核、已批准、已退回、已豁免、处理说明 |
| 关账报告 | 形成会议和审计材料 | 摘要、异常结论、证据索引、复核记录、审计摘要 |

关键交互：

- 创建关账工作区；
- 选择会计期间；
- 导入 CSV / Excel；
- 发起关账检查；
- 查看证据；
- 指派负责人；
- 标记已处理；
- 提交复核；
- 批准豁免；
- 退回处理；
- 生成关账报告；
- 导出报告。

关账工作台不承诺“自动关账”。它承诺的是 `Close Readiness Control`：把关账前的检查、证据、异常、责任和报告组织成可复核闭环。

## 5. 核心用户旅程

### 5.1 交付旅程：从客户项目到可验收试运行

```text
交付团队创建客户项目
        │
        ▼
选择或创建智能体模板
        │
        ▼
绑定技能、知识文件和数据源
        │
        ▼
配置模型、工具、权限和运行约束
        │
        ▼
发起试运行
        │
        ▼
查看工具调用、成果文件、错误详情和成本
        │
        ▼
复制为新版本或修正配置
        │
        ▼
形成验收记录
```

验收标准：

- 每次试运行都有运行编号、智能体版本、输入输出摘要和错误状态；
- 每个成果文件能追溯到运行和版本；
- 失败运行能看到原因、关联审计事件和修复入口；
- 客户项目不是一个松散聊天空间，而是可交付资产容器。

### 5.2 治理旅程：从运行记录到审计链

```text
治理方进入治理台
        │
        ▼
筛选失败运行或高成本运行
        │
        ▼
打开运行详情
        │
        ▼
查看智能体版本、模型、工具调用和策略决策
        │
        ▼
查看关联审计事件
        │
        ▼
确认责任人、版本依赖、数据访问和成本归因
        │
        ▼
导出审计记录或交给交付团队修正
```

验收标准：

- 治理方不需要读日志就能理解一次运行；
- 每个关键动作都有审计事件；
- 每个策略拒绝有可解释原因；
- 每次运行能关联成本、版本和请求编号。

### 5.3 关账旅程：从期间检查到报告

```text
财务用户创建关账工作区
        │
        ▼
选择账套和会计期间
        │
        ▼
导入或连接凭证、余额表、辅助账等证据来源
        │
        ▼
选择总账完整性检查模板
        │
        ▼
发起关账检查
        │
        ▼
系统生成证据和异常发现
        │
        ▼
责任人处理异常并补充说明
        │
        ▼
复核人批准、退回或豁免
        │
        ▼
生成关账就绪报告
```

验收标准：

- 关账结论必须能回看证据；
- 每个异常必须有关联控制项、证据、运行和责任人；
- 豁免必须有审批人、原因和审计事件；
- 报告不是 LLM 文本拼接，而是运行、证据、异常、复核和审计的快照。

## 7. 中文交互原则

中文化不是把英文菜单逐个翻译，而是重建产品语言层。用户看到的语言必须对应他们的任务、责任和下一步动作。

### 7.1 页面语言

页面标题、菜单、按钮、表格列、状态、空状态、错误提示、确认弹窗必须中文。

允许保留英文的内容：

- 产品名 Neptune；
- 路由路径，如 `/governance`；
- 代码标识符，如 `RunDto`；
- 协议字段，如 `requestId`；
- 第三方产品名，如 PostgreSQL、Redis、Langfuse；
- 技术缩写，如 ERP、CSV、Excel、API、MCP、SSE；
- 模型名和 provider 名称。

禁止在用户主界面直接出现：

- `Delivery Console`
- `Governance Console`
- `Business Workspace`
- `Run Lab`
- `Audit Events`
- `Agent Versions`
- `Cost Snapshot`
- `Policy Decisions`
- `Close Readiness`
- `Finding`
- `EvidenceArtifact`
- `HumanReview`

这些词可以存在于代码、路由、内部类型或开发者调试视图中，但用户主路径必须使用中文。

### 7.2 状态文案

| 内部状态 | 中文文案 |
| --- | --- |
| `running` | 运行中 |
| `completed` | 已完成 |
| `failed` | 失败 |
| `cancelled` | 已取消 |
| `created` | 已创建 |
| `idle` | 空闲 |
| `draft` | 草稿 |
| `active` | 已启用 |
| `inactive` | 已停用 |
| `pending_review` | 待复核 |
| `approved` | 已批准 |
| `rejected` | 已退回 |
| `waived` | 已豁免 |
| `blocked` | 被阻塞 |

### 7.3 空状态与错误文案

空状态必须说明下一步动作，不能只显示 `No data`、`Not found` 或 `Failed to load`。

| 场景 | 中文文案 |
| --- | --- |
| 没有客户项目 | 还没有客户项目。请先创建客户项目，再配置智能体和数据源。 |

### 7.4 交互动作

按钮必须使用清晰动词，避免抽象名词：

- `发起试运行`，不要写 `Run`；
- `查看审计链`，不要写 `Audit`；
- `提交复核`，不要写 `Submit`；
- `批准豁免`，不要写 `Approve Waiver`；
- `生成关账报告`，不要写 `Generate`；
- `导出审计记录`，不要写 `Export Audit Events`。

技术详情抽屉可以显示原始字段名，但必须同时提供中文标签和中文解释。

## 8. Solution Pack 如何验证平台内核

第一 Solution Pack 是中国 ERP 财务月结关账。它的价值不是证明 Neptune 会做财务，而是证明 Neptune 能承载高风险、强流程、强证据链的企业智能体生产场景。

### 8.1 验证维度

| 平台内核能力 | 关账场景压力测试 | 成立标准 |
| --- | --- | --- |
| 项目与环境 | 不同客户、账套、期间需要隔离 | 关账工作区能归属客户项目和会计期间 |
| 智能体版本 | 财务结果必须解释当时使用的规则和模板 | 每次运行绑定不可变智能体版本和规则版本 |
| 连接器 | ERP / CSV / Excel / mock 数据源差异大 | 数据源接入不污染平台对象 |
| 运行控制 | 检查任务可能失败、重试、取消 | 运行状态、事件、错误和请求编号完整 |
| 证据 | 财务结论必须有原始凭证和数据快照 | 每个证据有来源、hash、类型、关联运行 |
| 异常发现 | 智能体输出必须转成可处理业务对象 | 每个异常关联控制项、证据、严重性、责任人 |
| 人工复核 | 财务判断不能由模型最终决定 | 批准、退回、豁免都进入责任链 |
| 审计 | 关账材料可能被追溯 | 关键动作 append-only，能导出审计链 |
| 成本 | 财务共享中心关注规模化成本 | 用量按项目、运行、智能体、模型归因 |
| 评估 | 升级不能破坏历史规则表现 | 样例数据集能回归检查规则和报告质量 |

### 8.2 第一阶段规则范围

总账完整性检查优先覆盖：

1. 未过账凭证检查；
2. 会计期间状态检查；
3. 凭证编号连续性检查；
4. 现金 / 银行异常方向余额检查；
5. 大额手工凭证检查；
6. 关键科目本期波动异常检查。

第一阶段可以只真实实现其中一部分，其余使用 mock / sample data 验证产品闭环。重点不是规则覆盖率，而是平台链路是否成立：

```text
规则模板 -> 运行 -> 证据 -> 异常 -> 复核 -> 审计 -> 报告
```

### 8.3 不能从 Solution Pack 下沉到平台内核的内容

以下内容属于财务 Solution Pack，不属于 AgentOps Platform Core：

- 会计期间规则；
- 凭证编号规则；
- 科目余额方向规则；
- 关账报告模板；
- 总账完整性检查清单；
- 用友、金蝶等 ERP 字段映射；
- 财务异常分类；
- 财务复核角色默认配置。

平台内核只沉淀跨行业机制：

- 项目；
- 版本；
- 运行；
- 工具调用；
- 证据 artifact；
- 复核；
- 审计；
- 策略；
- 成本；
- 评估；
- 发布元数据。

## 9. 明确不做

第一阶段是 Strategy Prototype / Architecture MVP，不是完整生产运维平台，也不是财务产品大而全。

### 9.1 产品不做

- 不把聊天作为主界面；
- 不做通用聊天机器人工作台；
- 不做完整财务 SaaS；
- 不做完整财务核算模块；
- 不做复杂集团合并；
- 不做复杂 BI 报表；
- 不承诺自动关账；
- 不自动过账；
- 不自动批准豁免；
- 不替客户业务负责人做最终财务判断；
- 不做所有 ERP 深度连接；
- 不做通用自然语言规则编辑器。

### 9.2 平台不做

- 不提前建设 Neptune Cloud Control Plane；
- 不提前建设完整生产 CI/CD；
- 不提前建设大规模运维控制面；
- 不做 connector marketplace；
- 不做自动 rollback；

- 不做完整商业计费、发票和订阅系统；
- 不把第一 Solution Pack 写死到平台内核；
- 不因为财务场景修改 `neptune-engine` 为财务专用 runtime。

### 9.3 当前文档不做

- 不定义数据库迁移；
- 不定义 API 字段；
- 不定义前端组件实现；
- 不修改代码；
- 不修改 `neptune-engine`；

## 10. 执行检查表

后续任何 Neptune 产品设计、前端改造、服务规划或 Solution Pack 实现，都必须先回答以下问题：

1. 这个能力服务交付台、治理台还是关账工作台？
2. 它的目标用户是谁：交付团队、客户技术治理方、客户业务责任方，还是经济买方？
3. 它是否落到 `Run / Evidence / Finding / Review / Audit / Version / Cost` 事实链？
4. 它是否把聊天当成了主架构？如果是，必须重新设计。
5. 它是否把财务语义下沉到了平台内核或 `neptune-engine`？如果是，必须上移到 Solution Pack。
6. 它是否有中文页面标题、按钮、状态、空状态和错误恢复路径？
7. 它是否能解释版本、证据、责任人和审计链？
8. 它是否属于第一阶段明确不做的范围？如果是，不进入当前 MVP。

最终判断标准：

**Neptune 的第一阶段成功，不是做出一个会聊天的智能体产品，而是做出一条企业敢拿去试运行、交付团队能复制、治理团队能审计、业务团队能复核的 AgentOps 生产链路。**
